# Участие в разработке

Этот документ описывает практический порядок работы с репозиторием. Инженерные
правила находятся в [`AGENTS.md`](AGENTS.md), а правила оформления задач — в
[`docs/ISSUE_GUIDELINES.md`](docs/ISSUE_GUIDELINES.md).

## Перед началом работы

- Прочитайте [`README.md`](README.md) и актуальную документацию по затрагиваемой
  части проекта
- Ознакомьтесь с [`AGENTS.md`](AGENTS.md)
- Выберите существующую issue или создайте новую через шаблон GitHub
- Проверьте объём задачи, зависимости и пересечение с активными PR
- Не начинайте реализацию, если ожидаемый результат нельзя проверить по критериям
  готовности

## Работа с issue

Одна ветка и один PR обычно соответствуют одной issue.

Новая issue оформляется по
[`docs/ISSUE_GUIDELINES.md`](docs/ISSUE_GUIDELINES.md). Если во время работы
меняется объём задачи, после согласования нужно обновить описание issue, а не
оставлять решение только в комментариях или переписке.

## Ветка

Создавайте отдельную ветку от актуальной `main`.

Рекомендуемый формат имени:

```text
<type>/<issue-number>-<short-name>
```

Примеры:

- `feat/5-copy-result`
- `fix/12-provider-timeout`
- `docs/7-issue-guidelines`

Не смешивайте в одной ветке независимые изменения.

## Реализация

- Соблюдайте правила из [`AGENTS.md`](AGENTS.md)
- Разрабатывайте новую и изменяемую логику по TDD
- Не добавляйте абстракции и зависимости без необходимости
- Не выполняйте массовые косметические изменения вне объёма issue
- Поддерживайте код, тесты и документацию в согласованном состоянии
- Не добавляйте секреты, персональные данные и реальные пользовательские тексты

## Проверки

Перед открытием или обновлением PR выполните:

```bash
make lint-md
pnpm check
```

Если часть проверки невозможно выполнить локально, укажите это в описании PR и
объясните причину.

## Коммиты

- Используйте Conventional Commits
- Делайте коммиты атомарными
- Формулируйте сообщение по фактическому результату изменения
- Не включайте в коммит несвязанные файлы

Примеры:

```text
feat: add result copy action
fix: handle provider timeout
docs: document issue workflow
```

### Подготовка истории ветки

PR может содержать несколько коммитов. Каждый сохранённый коммит должен быть
самостоятельным, атомарным и понятным. Не нужно объединять независимые логические
изменения только ради искусственного правила «один PR — один commit»: история
ветки должна показывать последовательность законченных решений.

Перед финальным ревью объединяйте локально коммиты, которые не имеют
самостоятельной ценности:

- Коммиты с сообщениями `fixup`, `squash` или `WIP`
- Исправление опечатки или мелкого недочёта непосредственно предыдущего коммита
- Промежуточное сохранение работы
- Исправление замечания ревью, не являющееся самостоятельным логическим изменением
- Коммит, который сам по себе не даёт полезной и читаемой истории проекта

Не нужно автоматически объединять любой коммит, появившийся после ревью. Если
исправление самостоятельное, законченное и полезное как логическое изменение, его
можно сохранить отдельным коммитом.

Окончательный вид истории подготавливайте в таком порядке:

1. Завершите реализацию
2. Проверьте итоговый diff
3. До финального ревью, предпочтительно перед переводом PR из draft в ready, приведите историю рабочей ветки к окончательному виду
4. Повторно выполните обязательные проверки
5. Проведите финальное ревью актуальной версии ветки
6. Слейте подготовленный PR

Переписывание истории после финального approve нежелательно, потому что меняются
проверенные содержимое и SHA коммитов. Если история всё же была переписана, заново
проверьте diff, CI и применимость предыдущего ревью.

Для объединения, переупорядочивания и редактирования коммитов собственной рабочей
ветки используйте локальный interactive rebase:

```bash
git fetch origin
git log --oneline HEAD..origin/<рабочая-ветка>
git rev-parse origin/<рабочая-ветка>
git rebase -i origin/main
git push origin HEAD:refs/heads/<рабочая-ветка> \
  --force-with-lease=refs/heads/<рабочая-ветка>:<ожидаемый-SHA>
```

После `git fetch origin` убедитесь, что `git log HEAD..origin/<рабочая-ветка>`
не показывает чужих или иных неожиданных коммитов. Если показывает, остановитесь
и сначала разберитесь с ними. Затем сохраните SHA из `git rev-parse` как
`<ожидаемый-SHA>`, выполните rebase и подставьте этот SHA в команду push.

Неявный `--force-with-lease` сверяет удалённую ветку с локальным
remote-tracking ref. После `git fetch` этот ref уже может содержать коммит,
который не вошёл в переписанную историю. Явный lease сверяет удалённую ветку с
проверенным SHA: если она изменилась после проверки, push будет отклонён и не
перезапишет это состояние.

Обычный `git push --force` использовать запрещено: он отключает эти проверки и
может удалить чужие коммиты. Force-push допустим только в рабочую ветку, куда
гарантированно не пушат другие участники. Для совместно используемой рабочей
ветки не переписывайте историю. Переписывать историю `main` и других общих
веток запрещено.

После force-push повторно проверьте diff, выполните обязательные проверки и
проведите финальное ревью актуального HEAD.

Подготовленный PR обычно сливается через `Rebase and merge`. GitHub `Squash and
merge` не используется как основной способ очистки истории: коммиты, которые
нужно объединить, подготавливаются локально до финального ревью. Несколько
осмысленных атомарных коммитов можно оставить. Исключения должны быть явно
согласованы, а не становиться случайным выбором кнопки GitHub.

## Pull request

В описании PR укажите:

- что изменено
- как результат проверен
- какие ограничения или компромиссы остались
- изображения мобильного и настольного интерфейса для визуальных изменений
- `Closes #N` или `Fixes #N`, если PR полностью завершает issue

PR должен быть достаточно небольшим для последовательного ревью. Не добавляйте в
него изменения, которые не нужны для критериев готовности связанной issue.

Если реализация сознательно отклоняется от issue, сначала согласуйте решение и
обновите описание задачи.

## Приватность

В репозиторий, issue, PR, комментарии, тесты и примеры нельзя добавлять:

- личную переписку
- реальные адреса, фамилии, телефоны и номера квартир
- API-ключи и другие секреты
- необезличенные пользовательские тексты

Для примеров и фикстур используйте только вымышленные или полностью обезличенные
данные.
