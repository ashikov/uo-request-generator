# Правила работы с репозиторием

## Общие правила

- Использовать Conventional Commits
- Делать коммиты атомарными
- Не смешивать независимые изменения
- Перед финальным ревью приводить историю рабочей ветки к читаемому виду
- Сохранять самостоятельные атомарные коммиты и объединять локально промежуточные, `fixup`-коммиты и другие коммиты без самостоятельной ценности
- После переписывания опубликованной рабочей ветки использовать только `git push --force-with-lease` и повторно запускать обязательные проверки
- Не переписывать историю `main` и других общих веток
- Подробный порядок подготовки истории и доставки результата описан в [CONTRIBUTING.md](CONTRIBUTING.md#коммиты)
- Перед завершением работы запускать `make lint-md` и `pnpm check`
- Не добавлять секреты
- Не менять продуктовые или архитектурные решения молча
- Существенные решения фиксировать в документации или ADR
- Не выдумывать недостающие факты
- Поддерживать код, тесты и документацию в согласованном состоянии
- Писать код и идентификаторы на английском языке
- Писать документацию и интерфейс на русском языке

## Архитектура и код

- Сохранять архитектуру простой
- Не создавать абстракции и пакеты «на будущее»
- Не устранять дублирование ценой преждевременной, менее понятной или искусственно универсальной абстракции. Общий код следует выделять после появления устойчивого общего правила, а не только из-за внешнего сходства фрагментов.
- Писать код так, чтобы его назначение было понятно из структуры, типов и
  предметных имён
- Предпочитать предметные имена общим названиям вроде `data`, `result`, `item`,
  `helper`, `utils`, `service` и `manager`, если сущность можно назвать точнее
- При выборе новых предметных имён сверяться с [`CONTEXT.md`](CONTEXT.md)
- Не вводить новый синоним уже определённого предметного понятия без причины
- Если новое предметное название противоречит [`CONTEXT.md`](CONTEXT.md) или
  вводит другое имя для уже определённого понятия, явно указывать на конфликт
- Не закреплять конфликтующий термин без отдельного решения
- Обновлять [`CONTEXT.md`](CONTEXT.md) только после явного закрепления нового
  предметного термина
- Функция должна решать одну понятную задачу и оставаться достаточно короткой
  для последовательного чтения
- Избегать глубокой вложенности, предпочитать ранние возвраты и явные проверки
- Делать поток данных и зависимостей явным
- Не скрывать важное поведение в глобальном состоянии и неочевидных побочных
  эффектах
- Использовать TypeScript-типы и Zod-схемы как часть документации контрактов
- Проверять недоверенные данные на серверных и интеграционных границах. Клиентская валидация улучшает интерфейс и даёт раннюю обратную связь, но не защищает систему и не заменяет серверную проверку.
- При неоднозначном результате проверки безопасности, лимита или разрешения не выполнять платное или необратимое действие
- Не дробить простой код на множество одноразовых функций только ради
  формального соблюдения принципа «одна функция — одна задача»
- Не создавать абстракции ради абстракций
- Не переименовывать сущности только ради вкусовых предпочтений, если текущее
  имя уже предметное и понятное
- Предпочитать встроенные возможности стека
- Веб-сервер реализовывать на Fastify
- Интерфейс реализовывать обычными HTML, CSS и минимальным browser JavaScript
- Bootstrap 5 использовать как предпочтительный UI-слой интерфейса
- Сначала использовать стандартные Bootstrap components и utilities
- Добавлять custom CSS только когда возможностей Bootstrap недостаточно
- Не создавать отдельную Bootstrap-тему или дизайн-систему без подтверждённой необходимости
- Не добавлять frontend-фреймворк без подтверждённой сложности интерфейса
- Не добавлять шаблонизатор, пока страница остаётся статической
- Не собирать HTML строками в TypeScript
- Не помещать доменную логику в Fastify-маршруты
- Не допускать зависимости `packages/core` от Fastify, HTTP или браузерного кода
- Предпочитать прямой и читаемый поток запроса скрытой магии фреймворка
- Избегать лишнего клиентского JavaScript
- Не усложнять код ради предполагаемой производительности без подтверждённой проблемы, измерений и проверяемой цели оптимизации
- Не добавлять runtime-зависимости без необходимости
- Держать конфигурацию явной
- Не менять неявно публичные HTTP-контракты, коды ошибок и конфигурационные интерфейсы. Такие изменения должны сопровождаться актуализацией схем, тестов и документации.
- Не использовать `any`
- Использовать TypeScript strict
- Комментарии в собственном коде писать на русском языке
- Не добавлять комментарии, которые пересказывают очевидное поведение кода
- Комментировать причины, ограничения, компромиссы и неочевидные решения
- Разрабатывать новую и изменяемую логику по циклу TDD: падающий тест,
  минимальная реализация, рефакторинг на зелёных тестах
- Обеспечивать достаточные для диагностики работы приложения и контроля расходов
  логи и метрики, не включая в них пользовательские тексты, персональные данные
  и секреты
- Не использовать LLM как источник фактов или законодательства

## Стратегия тестирования

- Тесты должны защищать наблюдаемое поведение, публичный контракт или конкретный
  инвариант, а не внутреннюю форму текущей реализации
- Выбирать самый простой уровень теста, который надёжно проверяет требуемое
  поведение. Не использовать integration или browser test, если тот же контракт
  полноценно проверяется небольшим unit test
- Не переimplementовывать в тестах семантику внешних инструментов, протоколов и
  форматов. Если поведение можно проверить через реальный публичный интерфейс
  инструмента или существующую библиотеку, предпочитать это собственному parser
  или interpreter
- Если для поддержки теста приходится добавлять всё больше специальных случаев,
  обходов или вспомогательной логики, остановиться и пересмотреть уровень
  проверки вместо дальнейшего усложнения test harness
- Предпочитать небольшой надёжный контракт широкому тесту с известными false
  positive или false negative
- Одну гарантию проверять на наиболее подходящем уровне. Не дублировать один и
  тот же контракт в unit, integration и browser tests без отдельной причины
- Ожидаемые значения и независимые test anchors не выводить из реализации,
  которую они должны проверять
- При падении теста сначала определить, нарушено ли реальное поведение или
  ошибочна модель теста. Не менять production-код только ради удовлетворения
  неверного тестового предположения
- Mutation-, adversarial- и regression-тесты должны защищать реалистичный способ
  нарушения полезного продуктового или технического инварианта. Не добавлять и
  не сохранять случаи, которые в основном проверяют сложность самого test
  harness
- Если последовательные исправления тестов обнаруживают всё новые варианты одной
  и той же проблемы в тестовой абстракции, упростить дизайн теста или сменить
  способ проверки вместо бесконечного добавления edge cases
- Граничные случаи выбирать из требований, реальных рисков и известных
  регрессий, а не стремиться перебрать все теоретически возможные комбинации
- Точную формулировку UI-текста закреплять тестом только когда она является
  явным продуктовым требованием, acceptance criterion или частью доступности и
  пользовательского контракта
- Не считать количество тестов, mutation cases или coverage самостоятельной
  целью. Дополнительный тест оправдан, если он защищает отдельный риск или даёт
  существенно более сильное доказательство корректности

## Документация

- Использовать естественный и практичный язык
- Процесс live LLM regression eval и semantic review описан в [`docs/LLM_BENCHMARK.md`](docs/LLM_BENCHMARK.md)
- Избегать корпоративного маркетингового языка и хайпа
- Один абзац должен выражать одну законченную мысль
- Не дублировать одну информацию по нескольким документам
- Не описывать будущие возможности как уже реализованные
- Не использовать реальные адреса, фамилии, телефоны и номера квартир в примерах
- Для конфигурационных файлов предпочитать YAML, если инструмент не требует
  другого формата или исполняемой конфигурации

## Списки

- Не использовать точки с запятой
- Короткие пункты оформлять без знака в конце
- Законченные предложения оформлять с точкой.
- Если пункт состоит из нескольких предложений, каждое предложение заканчивать
  точкой.
- Внутри одного списка сохранять единообразное оформление

## Окончание файлов

Поддерживаемые текстовые и кодовые файлы должны заканчиваться ровно одним
переводом строки без дополнительной пустой строки перед EOF.

Если в будущем появится `README.en.md`, его нужно поддерживать синхронно с
`README.md`. В текущем задании `README.en.md` не создавать.
