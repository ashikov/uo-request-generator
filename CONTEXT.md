# Предметный контекст

Сервис помогает жителю подготовить одну заявку для управляющей организации по
одной наблюдаемой проблеме.

## Канонический язык

**Заявка**

Текст обращения жителя в управляющую организацию по наблюдаемой проблеме. Не
называть заявкой пользовательский ввод или внутренний черновик.

**Описание проблемы**

Свободный пользовательский ввод о проблеме. Это не готовая заявка и не её
готовое описание: сведения из него распределяются по смыслу.
В коде этому соответствует входное поле `description`.

**Наблюдаемая проблема**

Один самостоятельный дефект или нарушение, которое житель может описать по
известным ему фактам. Одна проблема может включать связанные признаки, места
проявления, последствия и желаемые действия.
В структурированном черновике она представлена полем `problem`.

**Несвязанные проблемы**

Несколько самостоятельных наблюдаемых проблем, для которых нужны отдельные
заявки. Не считать несвязанными связанные проявления одной ситуации.

**Последствия**

Уже наблюдаемый эффект проблемы, неудобство, риск или повреждение, о котором
сообщил пользователь. Это не предполагаемая причина и не неподтверждённый
прогноз.
Во входных данных это поле `consequences`.

Поле `impact` расширенного черновика имеет более широкую роль. Оно сохраняет
переданные последствия и риски, а при безопасном непосредственном основании
может также содержать выведенное практическое значение проблемы или явно
обозначенный потенциальный риск. Вывод не становится установленным фактом.

**Желаемые действия**

Ожидание пользователя от управляющей организации. Это не подтверждённый способ
устранения проблемы и не обещание выполнить работы.
Во входных данных это поле `desiredActions`. Процедурный план сохраняет эти
действия и может дополнять их только минимально необходимыми действиями той же
цели.

**Процедурный план первичной заявки**

Внутренняя часть черновика, которая отдельно представляет предварительную
проверку, действия по устранению и проверку результата. В коде это поле
`actionPlan` со смысловыми ролями `preliminaryCheck`, `remedyActions` и
`resultCheck`.
Канонические правила заполнения описаны в
[`docs/REQUEST_RULES.md`](docs/REQUEST_RULES.md#процедурный-план-первичной-заявки).

**Черновик**

Внутренний структурированный результат LLM до детерминированного
форматирования. Для одной связанной проблемы он содержит части будущей заявки,
а при нескольких несвязанных проблемах сообщает об этом исходе.
В коде это `RequestDraft`, а для успешной ветки — `GeneratedRequestDraft`.

**Расширенный черновик первичной заявки**

Provider-independent структурированные части одной первичной заявки до
детерминированного форматирования: наблюдаемая проблема, существенные
обстоятельства, последствия, практическое значение и потенциальные риски,
предмет проверки, проверяемый предмет проблемы, процедурный план и
предупреждения. В коде это `PrimaryRequestDraft`. Проверяемый предмет проблемы
содержит только предметный факт и дословные фрагменты исходного ввода, а не
выбранный нормативный акт. Успешная provider-facing ветка содержит те же части
вместе с полем `outcome` и после строгой локальной проверки передаётся renderer
вместе с исходным вводом для проверки происхождения evidence.

**Явное подтверждение предмета двери**

Структурированный пользовательский факт `isCommonAreaDoor`. Значение `true`
означает, что пользователь явно подтвердил входную дверь многоквартирного дома
или дверь помещения общего пользования, а не дверь квартиры или частного
помещения. Подтверждение не передаётся LLM и служит самостоятельным
backend-проверяемым основанием для разрешения предметного нормативного модуля.
Значение `false` или отсутствие поля означает fail closed.

**Нормативный модуль**

Хранящийся в `packages/core` типизированный предметный нормативный текст с
областью применимости, официальными источниками и датой их проверки. Backend
подключает модуль детерминированно только при явном пользовательском
подтверждении предмета и проверенном происхождении evidence из исходного ввода.
Точное совпадение evidence само по себе не доказывает смысловую применимость.
LLM не выбирает модуль или нормативный акт.

Общие нормативные основания добавляются в каждую готовую заявку. Предметный
нормативный модуль добавляется только для подтверждённого предмета проблемы и не
формирует процедурный план. Подробный контракт находится в
[`docs/REQUEST_RULES.md`](docs/REQUEST_RULES.md#предметный-нормативный-модуль).

**Результат генерации**

Типизированный исход обработки запроса: готовая заявка или сообщение о
нескольких несвязанных проблемах. Не использовать как синоним черновика или
готовой заявки.
В коде это `GenerateRequestOutcome`.

**Готовая заявка**

Успешный публичный результат с `title`, `body` и `warnings`, пригодный для
передачи управляющей организации. Не называть готовой заявкой черновик или
произвольный текст до успешной обработки.
В коде это `GenerateRequestResult`.
