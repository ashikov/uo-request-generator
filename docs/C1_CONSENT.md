# Отдельное согласие Ц1

Решение оператора от 15 сентября 2026 года для #264 утверждает текст, версию,
SQLite ledger, срок хранения evidence и расширение остаточного DOM-риска #193.
Документ публикует безопасную выжимку решения. Рабочий диалог, закрытые
подтверждения и частные эксплуатационные сведения не публикуются.

## Текст и неизменяемая версия

Версия: `c1-2026-09-15-r1`.

> Я даю согласие на обработку персональных данных, которые указываю в этой форме, исключительно для подготовки и возврата мне текста одной заявки в управляющую организацию. Для этой цели введённые данные могут быть переданы внешнему сервису на базе LLM, используемому оператором для подготовки текста заявки. Согласие действует до достижения указанной цели или до его отзыва. Отозвать согласие можно, написав на [zayavka@ashikov.ru](mailto:zayavka@ashikov.ru).

Текст утверждён оператором целиком. Разработчик не изменяет юридическую
формулировку. Содержательное изменение требует новой версии, прежняя версия
для другого текста не используется. Связь версии с утверждённым текстом
сохраняется в истории документа и приложения, а не дополнительным полем ledger.
UI, browser request, server-side validation и ledger используют точную строку
без нормализации, автоматического обновления или принятия старых версий.

Это отдельное согласие только для подготовки и возврата одной заявки — Ц1.
Один первоначально неустановленный checkbox не объединён с предупреждением
о третьих лицах, политикой, CAPTCHA или другими подтверждениями. Согласие
не распространяется на третьих лиц и не является специальным согласием.
Ц2, Ц3 и Ц4 сохраняют самостоятельные основания из #182. Отказ или отзыв Ц1
не отзывают их автоматически.

## HTTP и browser flow

Browser требует checkbox до получения CAPTCHA controller/token и submit,
показывает доступную ошибку и отправляет только `consentAccepted: true`
и `consentVersion: "c1-2026-09-15-r1"`, без повторной отправки текста согласия.
Существующая загрузка public configuration не является получением согласия.

Серверный порядок:

```text
availability guard → body limit / JSON parsing → transport validation
→ client limiter → допустимый CAPTCHA-поток
→ проверка consentAccepted === true и точной consentVersion
→ transactional durable receipt → x-consent-receipt-id
→ safeguard → LLM
```

В транспортной схеме поля согласия допускаются для последующей проверки.
Семантическая проверка выполняется после CAPTCHA: отсутствующее, непринятое,
неизвестное или устаревшее согласие возвращает существующий `400 validation_error`
с прежним `{ error: { code, message, requestId } }`. Эти ответы не обещают
отсутствия независимой обработки CAPTCHA по Ц3. Невалидный предметный ввод,
ошибки JSON и transport limit по-прежнему отклоняются раньше.

При подключённом LLM отсутствие ledger, ошибка записи или транзакции
останавливают дальнейшую обработку с существующим `500 internal_error`.
Локальный запуск без подключённого LLM и ledger сохраняет диагностический
`503 generation_provider_unavailable` без создания receipt. Нет in-memory fallback,
очереди отложенной записи или продолжения LLM после ошибки evidence.
Поля согласия и CAPTCHA token отделяются на HTTP-границе и не передаются LLM.

После durable creation каждый ответ этого запроса содержит
`x-consent-receipt-id`: успешный результат, отказ safeguard, `multiple_issues`,
ошибки LLM и другие downstream failures. До создания receipt заголовка нет.
Browser читает его до разбора тела и показывает отдельно от результата,
включая ошибочные ответы. Код не добавляется в clipboard или browser storage.

Receipt — opaque вспомогательный locator для поддержки и отзыва, не identity,
authentication или proof of person. То же ограничение сохраняется для
`requestId`, который используется только для технической корреляции.
Публичных lookup/delete endpoints нет.

## Узкий долговечный ledger

Встроенный `node:sqlite` использует одну таблицу и ровно следующие поля:

| Поле | Значение |
| --- | --- |
| `consentReceiptId` | Созданный сервером случайный opaque UUID |
| `requestId` | Корреляционный UUID текущего HTTP-запроса |
| `consentVersion` | Точная поддерживаемая неизменяемая версия |
| `serverTimestamp` | Серверное время получения принятого согласия в UTC |
| `status` | `accepted` либо `revoked` |
| `revocationTimestamp` | Только для `revoked`, время подтверждённого отзыва в UTC |

У `accepted` nullable SQL-колонка отзыва имеет `NULL`, а возвращаемая запись
не содержит `revocationTimestamp`. Ограничение SQL запрещает заполненное время
для `accepted` и его отсутствие для `revoked`.

В ledger нет пользовательского ввода, результата, IP, cookie, CAPTCHA token,
подписей, документов заявителя или новых технических полей. Он не является
историей заявок или основой будущего audit storage. Consent receipt не добавляется
в существующие structured application events.

Запись выполняется в транзакции с rollback journal `DELETE`,
`synchronous=EXTRA` и `secure_delete=ON`. Receipt возвращается вызывающему коду
только после успешного `COMMIT`. Эти настройки не означают гарантию хранения
при неисправности носителя, уничтожение всех внешних копий или выполнение №179.
Детали настроек установлены по [документации SQLite](https://www.sqlite.org/pragma.html#pragma_synchronous).

Приложение без контейнера требует `CONSENT_LEDGER_FILE` для подключённого LLM.
Файл и его закрытая область создаются с ограниченными правами. В Compose
используется один отдельный writable named volume при сохранении read-only root
filesystem. Поставляемая точка монтирования — типовой интерфейс приложения,
не сведения о частном operational stack. Root приложения не становится writable.
Отсутствие или недоступность файла не обходятся временным хранилищем.

Доступ имеет только application runtime в необходимом объёме и оператор.
Это требует фактической проверки прав persistent volume до production.
Замена application container не должна уничтожать volume. Удаление volume
не используется как штатная команда обслуживания consent evidence.

Отдельных application-managed backups нет по решению оператора. До production
оператор отдельно подтверждает наличие либо отсутствие автоматических snapshots
и backups платформы. Обнаруженные копии включаются в ту же область хранения,
доступа, удаления и подтверждения результата. Их отсутствие из кода не выводится.

## Отзыв, срок хранения и удаление

Отзыв принимается на `zayavka@ashikov.ru` по
[процедуре #184](PERSONAL_DATA_PROCESSING.md#отзыв-ц1-и-реакция-на-случайные-данные).
Индивидуальный поиск и запись подтверждённого результата выполняются после
соразмерной проверки заявителя и связи с обработкой. Знание receipt недостаточно.
Ledger отражает отзыв как `revoked` с `revocationTimestamp`; повторная фиксация
того же отзыва не меняет timestamp и не продлевает срок. Отсутствующая запись
не превращается в выдуманное подтверждение. Изменение ledger не подтверждает
прекращение либо уничтожение данных у внешних получателей и не снимает `blocked`
по #184.

**Операторский срок evidence — три календарных года:**

- Для `accepted` — с `serverTimestamp`
- Для `revoked` — с `revocationTimestamp`
- Для receipt перед неуспешной генерацией — то же правило

Для 29 февраля годовщина приходится на последний день февраля соответствующего
года. Цель хранения после генерации и отзыва — доказать получение согласия,
обработать связанный отзыв, обращение, проверку или спор. Это решение оператора,
а не готовый срок, прямо установленный 152-ФЗ. Согласие Ц1 не описывается как
автоматическое основание продолжать любую обработку после отзыва.

Статьи 9, части 1–3, и 5, части 5 и 7, требуют отдельного доказуемого согласия,
соразмерности и ограничения хранения необходимостью цели. В проверенных общих
нормах фиксированного срока consent evidence нет. Применимые прекращение и
уничтожение после отзыва регулируются статьёй 21, частью 5.
[Официальный текст 152-ФЗ](http://ips.pravo.gov.ru/api/ips/legislation/document?baseid=None&hash=98490812b3409e2a8d78a11ca9010f434ea3d9250a11dbbdb78690cd5551bdd6)
повторно прочитан 15 сентября 2026 года для этих норм.

По истечении срока оператор удаляет запись, если нет конкретной действующей
необходимости сохранить evidence для незавершённого обращения, проверки или
спора. Основание, защищённый receipt и пересмотр необходимости фиксируются
в закрытом metadata-only журнале #184, без дополнительных полей ledger.
Продление не применяется автоматически и не становится бессрочным.

Удаление выполняется локальной командой после проверки исключений.
`preview-expired` ничего не удаляет. `delete-expired` требует явного подтверждения
проверки оснований и готовности применимого процесса подтверждения уничтожения.
Защищённые receipt передаются через повторяемый `--protect`. Ошибка либо
отсутствие обязательного подтверждения не обходятся автоматическим SQL `DELETE`.
Команду удаления оператор выполняет при наступлении сроков и пересмотре
исключений. Фоновое удаление без проверки закрытых исключений не реализовано.

Для локального обслуживания используется собранная команда
`node apps/web/dist/consent-ledger-command.js`. Её аргументы — команда,
закрытый файл ledger и для индивидуальных операций receipt. Команды:

- `find` — найти evidence после проверки заявителя
- `revoke` — отразить подтверждённый отзыв после проверки заявителя
- `preview-expired` — проверить кандидатов к удалению без изменения записей
- `delete-expired` — удалить истёкшие записи с учётом явно защищённых receipt

Индивидуальная проверка подтверждается `--request-verified`; этот флаг —
декларация оператора о выполненной процедуре, а не техническая аутентификация.
Для удаления обязательны `--holds-reviewed` и `--destruction-evidence-ready`.
Вывод команды содержит закрытое evidence, не предназначен для GitHub или
публичных application logs. Команда не создаёт БД при неверном расположении
существующего ledger. Рабочий экземпляр и обслуживание одного ledger оператор
координирует; SQLite-транзакции не заменяют организационную проверку.

**Отдельный нормативный срок:** акт и применимая выгрузка подтверждения
уничтожения хранятся три года с уничтожения по
[приказу Роскомнадзора №179](http://publication.pravo.gov.ru/Document/View/0001202211290008).
Этот срок не является основанием срока consent ledger. Для применимой
автоматизированной обработки требуются акт и выгрузка журнала событий,
для неавтоматизированной — акт, для смешанной — оба.

Простой SQL `DELETE`, `secure_delete`, вывод команды или наличие записи в журнале
обращений сами по себе не объявляются достаточным подтверждением №179.
Фактические применимость и получение обязательных подтверждений устанавливаются
оператором до реального удаления. Пробелы подтверждения уничтожения из #184
сохраняются. Если нужны изменения приложения, они оформляются отдельной
атомарной Task по [ISSUE_GUIDELINES.md](ISSUE_GUIDELINES.md), а не новой общей
подсистемой аудита внутри #264.

## Расширение принятого DOM-риска #193

Оператор 15 сентября 2026 года принял для public beta техническую доступность
checkbox state, отображаемого утверждённого текста и immutable version,
а после ответа — `consentReceiptId` постоянно загруженному same-document
CAPTCHA script. Отдельная изоляция или mitigation этим решением не требуются.

Это расширение состава DOM-visible values в прежней границе доступа, а не
доказательство фактической передачи CAPTCHA-получателю. Script сохраняет
возможность чтения после `reset` виджета до уничтожения документа. Opaque
receipt не даёт личности или публичного доступа к ledger, пользовательский
payload намеренно не добавляется в ledger. Риск сохраняется, #193 не переоткрывается.

Characterization test с подменённым classic script читает новые значения
и их последующие изменения, включая receipt на downstream failure. Он проверяет
техническую возможность доступа, а не поведение реального провайдера.
Исходные [triggers #193](PERSONAL_DATA_PROCESSING.md#обязательный-пересмотр)
сохраняются. Решение отдельно пересматривается при смене provider/script или
загрузки, публичном lookup, расширении ledger, подтверждении фактической передачи
значений или существенном изменении DOM/trust boundary.

## Проверка и границы готовности

Route tests проверяют CAPTCHA до consent validation, receipt до LLM,
fail closed и заголовок на последующих ошибках. Unit tests работают с реальным
SQLite в синтетических временных файлах и проверяют reopen, минимальную схему,
отзыв, сроки, исключения и отказ записи. Browser tests проверяют checkbox,
доступную ошибку, точный текст/версию, receipt и расширенный DOM-доступ.
Контейнерные проверки используют только изолированный синтетический стенд.

Реализация и локальные проверки не подтверждают production-права, отсутствие
snapshots/backups платформы, необходимые подтверждения уничтожения или готовность
задач #184/#169. Закрытые фактические проверки выполняются отдельно до применимых
production-действий. LLM semantics, provider selection, решения статей 12/22,
задача #190 и Draft PR #268 не изменяются.
