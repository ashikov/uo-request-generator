# Повторное обращение в управляющую организацию

## Статус и границы

Спецификация для [#175](https://github.com/ashikov/uo-request-generator/issues/175)
в составе [Epic REPEAT #195](https://github.com/ashikov/uo-request-generator/issues/195).
Это проект отдельного профиля, а не описание уже доступной функции. Поставка
профиля требует реализации, независимого review и live semantic qualification.
Первичная заявка сохраняет контракт из [REQUEST_RULES.md](REQUEST_RULES.md).

Повторное обращение помогает изложить результат предыдущего взаимодействия с УО
и попросить рассмотреть оставшуюся проблему. Пользователь явно выбирает этот
профиль. Система не определяет его по ключевым словам, не отправляет документ
и не квалифицирует действия УО как нарушение или бездействие.

В первый срез входят одна проблема и одно предыдущее обращение. Связанные этапы
рассмотрения этого обращения допустимы в его кратком изложении. Несколько
самостоятельных обращений с разными проблемами не объединяются. Файлы, OCR,
серверная история, учётные записи и жалоба в компетентный орган исключены.

## Пользовательский сценарий

1. Пользователь выбирает «Повторное обращение в УО».
2. Кратко описывает предыдущее обращение и текущее состояние одной проблемы.
3. Отмечает, получен ли ответ, не получен или это неизвестно. При полученном
   ответе указывает его содержание.
4. При необходимости раскрывает дополнительные сведения: реквизиты, выполненные
   действия и результаты осмотра, нерешённые вопросы, новые факты, место и
   желаемые действия.
5. После обычных проверок защиты и согласия получает документ либо понятный
   отказ. Проверяет результат и копирует его в свой канал подачи.

Форма не требует точной даты, номера, дословной переписки или юридической оценки.
Вместо полного предыдущего обращения и ответа допустимо их краткое изложение.
Перед вводом переписки форма просит удалить идентифицирующие сведения и оставить
только относящиеся к проблеме факты. Автоматическое обезличивание не обещается.

## Входной контракт

`RepeatRequestInput` — отдельная строгая схема в `packages/core`. Она не
расширяет `GenerateRequestInput` и не добавляет неизвестные поля первичному
профилю. Длины считаются в UTF-16 code units, как в текущем HTTP/core-контракте.

| Поле | Обязательность | Значение и предел |
| --- | --- | --- |
| `previousRequest` | Обязательно | Текст или краткое содержание предыдущего обращения, 10–2000 символов |
| `currentState` | Обязательно | Наблюдаемое состояние проблемы сейчас, 10–2000 символов |
| `response` | Обязательно | Один из трёх вариантов ниже |
| `previousRequestDate` | Необязательно | Календарно допустимая дата `YYYY-MM-DD` |
| `previousRequestNumber` | Необязательно | Указанный пользователем номер, 1–80 символов |
| `performedActions` | Необязательно | Известные действия УО и результаты осмотра, замеров или работ, 1–1000 символов |
| `unresolvedQuestions` | Необязательно | Что осталось нерешённым или без содержательного ответа, 1–1000 символов |
| `newFacts` | Необязательно | Новые связанные обстоятельства после первого обращения, 1–1000 символов |
| `location` | Необязательно | Дополнительно указанное место, 1–120 символов |
| `desiredActions` | Необязательно | Желаемые действия сейчас, 1–500 символов |

Варианты `response` образуют строгий discriminated union:

- `{ status: "not_received" }` — пользователь сообщает об отсутствии ответа
- `{ status: "unknown" }` — пользователь не располагает сведениями об ответе
- `{ status: "received", text, date? }` — содержание ответа 1–2000 символов и
  необязательная календарно допустимая дата `YYYY-MM-DD`

`desiredActions`, состоящее только из удаляемого префикса `Прошу:` и пробелов,
отклоняется до provider, как в первичном профиле.

Дата ответа без полученного ответа, неизвестный status, посторонние поля,
пустые обязательные сведения и превышения лимитов отклоняются до provider.
Необязательные пустые поля browser не отправляет. Сумма длин всех строковых
значений, кроме `response.status`, ограничена 7000 символами. Этот общий предел
ограничивает стоимость длинной истории независимо от распределения по полям.

Проверка минимальной длины применяется к тексту без пробелов по краям.
Backend сохраняет содержимое проверенных полей без смыслового исправления.
Однострочные реквизиты не допускают CR/LF и управляющие символы. Номер не
проверяется на существование и не извлекается моделью из свободного текста.
Неизвестные реквизиты отсутствуют, а не заменяются догадкой или шаблонной датой.

Наличие текста длиной 10 символов само по себе не доказывает достаточность
истории. Когда из содержания невозможно безопасно составить повторное
обращение, действует отдельный исход `insufficient_history`.

## Ответственность LLM и backend

Backend владеет выбранным профилем, строгим входом, точными реквизитами,
состоянием ответа, ограничениями, нормативным текстом и окончательной сборкой.
Реквизиты не передаются в provider user message. Они вставляются только из
проверенного входа, поэтому модель не может заменить номер или дату.

Один provider-вызов естественно нормализует только описательные части. Он
сохраняет участников, условия, отрицания, последовательность событий, результаты
действий и различие между сообщением УО и наблюдением пользователя. Переданное
в ответе УО «работы выполнены» остаётся сообщением УО, если пользователь не
подтвердил результат самостоятельно.

Модель не придумывает сроки, уведомления, осмотры, измерения, работы, документы,
причины, нарушение или обязанность конкретного органа. Формальный ответ не
превращается в отсутствие ответа. Неизвестность не превращается в отсутствие
действий. Фраза «ничего не сделали» не отменяет явно переданный факт частичного
выполнения. При неустранимом содержательном противоречии модель возвращает
`insufficient_history`, а не выбирает удобную версию.

Новые потенциальные риски и обогащение первичной заявки не входят в этот профиль.
Здесь нужна точная нормализация истории. Исходы #307/#313 не переоцениваются,
отклонённые prompt/schema не переиспользуются.

## Черновик и материализация

Provider возвращает строгий union с `outcome`:

- `generated` — все поля `GeneratedRepeatRequestDraft` ниже
- `multiple_issues` — только `outcome`, без частичного документа
- `insufficient_history` — только `outcome`, без частичного документа

| Поле успешного provider draft | Смысл | Максимум |
| --- | --- | ---: |
| `title` | Краткий заголовок повторного обращения | 120 |
| `originalProblem` | Наблюдаемая проблема из предыдущего обращения | 800 |
| `previousRequestSummary` | Ранее заявленные требования и существенная история | 1200 |
| `responseSummary` | Содержание полученного ответа с явной атрибуцией УО либо `null` | 1200 |
| `performedActions` | Подтверждённые действия и результаты либо `null` | 1000 |
| `currentState` | Наблюдаемая проблема сейчас, без замены сообщением УО | 1600 |
| `unresolvedQuestions` | Нерешённые вопросы или требования либо `null` | 1000 |
| `circumstancesToVerify` | Существенные неизвестные обстоятельства либо `null` | 600 |
| `newFacts` | Новые связанные факты после обращения либо `null` | 1000 |
| `warnings` | До пяти коротких замечаний для проверки пользователем | 200 на замечание |

Все поля присутствуют. Неизвестная необязательная роль имеет значение `null`,
а не выдуманное содержание или пустую строку. Описательные поля — однострочные
непустые строки. Провайдеру не передаются законодательство и идентификаторы
нормативных модулей. Schema не содержит реквизиты и требования документа.

`RepeatRequestDraft` — отдельный материализованный черновик. Он содержит
проверенные описательные поля, реквизиты из входа, `responseStatus`, исходное
`location` и ровно один backend-owned `requestItems`. Он не является
`PrimaryRequestDraft` и не вводит универсальную модель дела.

`materializeRepeatRequestDraft` повторно проверяет вход и provider draft,
запрещает ненулевой `responseSummary` при `not_received`/`unknown` и требует
ненулевой `responseSummary` при `received`. Без исходного `performedActions`
выполненные действия допустимы только когда пользователь явно подтвердил их
в предыдущем обращении или текущем состоянии. Действия, о которых сообщает
только УО, остаются в `responseSummary` с этой атрибуцией и не становятся
подтверждённым результатом. Эту смысловую применимость проверяет semantic review,
а не наличие непустого поля или дословной цитаты.

Сведения о дате/номере, придуманные внутри описательного поля вопреки prompt,
остаются генеративным риском. Детерминированная вставка реквизитов не доказывает
отсутствие таких ошибок во всём документе. Нужна обязательная live-проверка.

Если `desiredActions` есть, материализатор сохраняет его целиком как один пункт
после тех же presentation-only преобразований, что определены для первичного
профиля. В частности, условия и отрицания не сокращаются. Без явного требования
используется фиксированный пункт:

> Повторно рассмотреть описанную проблему с учётом результата предыдущего обращения, сообщить о результатах рассмотрения и при подтверждении нерешённой проблемы принять меры по её устранению

Это просьба пользователя, а не утверждение об установленном нарушении, наличии
бездействия, сроке ответа или конкретном ремонте. Рядом с явным требованием
автоматический пункт не добавляется.

## Детерминированный документ

`renderRepeatRequestDraft` формирует `RepeatRequestResult` с `title`, `body` и
`warnings`. Порядок абзацев фиксирован:

1. Напоминание об исходной проблеме
2. Блок `Предыдущее обращение:` с известной датой/номером и краткой историей
3. Результат рассмотрения: полученный ответ либо фиксированное пояснение статуса
4. Подтверждённые действия и результаты, если они известны
5. Текущее состояние проблемы
6. Нерешённые вопросы, существенные обстоятельства для проверки и новые факты
7. Дополнительно указанное место, если оно есть
8. Применимые проверенные нормативные основания
9. Раздел `Прошу:` с одним нумерованным пунктом

Для `not_received` используется «Ответ на предыдущее обращение не получен».
Для `unknown` — «Сведения об ответе на предыдущее обращение отсутствуют».
Эти статусы не утверждают, что ответ не отправлялся, срок истёк или УО нарушила
обязанность. Неизвестная дата/номер просто не печатаются. Описательные роли не
повторяют один и тот же факт ради заполнения всех секций. Ненужные заголовки
и пустые абзацы не создаются. Предупреждения находятся вне копируемого `body`.

Лимит `title` — 120 символов, `body` — 8000, `warnings` — пять по 200.
Более длинный результат не обрезается и не показывается как готовый документ.
Отдельный предел нужен для истории обращения и не меняет 2500 символов
первичного профиля. Успешная проверка каждого поля отдельно не заменяет проверку
полного результата с реквизитами, нормативными основаниями и пунктом требования.
Принятый вход не гарантирует, что модель уложит все существенные сведения в
допустимый документ: в таком случае возвращается контролируемый отказ.

## Нормативная граница

Первый профиль не вводит новые сроки ответа, правовую оценку бездействия,
процедурные нормы или специальные требования к документам. Повторное обращение
по-прежнему адресовано УО, а не органу надзора.

Кандидат на повторное использование — существующий `COMMON_LEGAL_BASIS_BLOCK`:
общая обязанность содержания имущества и приём/рассмотрение обращений.
Перед включением профиля нужно отдельно подтвердить актуальность источников
и применимость обоих абзацев к поддержанному сценарию. Спецификация не является
новой правовой проверкой и не разрешает утверждать результат проверки источников.

В offline-core существующий блок используется без изменений только как
кандидат для сборки и оценки длины документа. Этот код не подключается к HTTP
или форме до закрытия gate. Он не добавляет утверждений о сроках или нарушении.
Проверка 04.11.2026 не завершена: официальный текст ЖК РФ на pravo.gov.ru
и PDF постановления №416 в архиве Правительства не удалось загрузить.
Доступные исторические разъяснения прокуратуры подтверждают общую область
норм, но не действующую редакцию. Для включения нужны актуальные источники
и подтверждение применимости к обслуживанию общего имущества данным УО.

Предметные модули в первый срез не включаются. Наличие предмета в старом ответе
УО не доказывает предмет текущей нерешённой проблемы. Нет поля подтверждения
предмета и нет переноса primary `subject/evidence` в новую историю. Добавление
предметных норм потребует отдельного сценария и контракта применимости.

## HTTP, UI и защита расходов

Для нового профиля планируется `POST /api/generate/repeat`. Существующий
`POST /api/generate` и его строгий primary payload сохраняются. Отдельный endpoint
позволяет использовать профильные лимиты, не делая старые клиенты зависимыми
от новой union-схемы. Выбор endpoint определяется явным выбором пользователя.

Ответ успеха имеет тот же набор полей, но отдельную result-схему с пределом
8000. Browser проверяет результат согласно выбранному профилю. Ошибки сохраняют
форму `{ error: { code, message, requestId } }`. `multiple_issues` просит
разделить проблемы, `insufficient_history` просит уточнить прежнее обращение
и его результат. Автоматического уточняющего LLM-вызова и retry нет.
Невалидный/слишком длинный provider draft возвращает контролируемую ошибку
генерации без публикации частичного результата.

Оба endpoint используют одни client/global limiter и active-слоты. Cookie
клиента для `/api/generate` должна покрывать и вложенный endpoint. Новый маршрут
не создаёт отдельный дневной бюджет и не обходится сменой профиля. Порядок
availability → transport validation → client limiter → CAPTCHA → consent receipt
→ global safeguard → provider сохраняется. HTTP body limit рассчитывается
из всех профильных полей, максимального JSON-escaping и существующих transport
полей, а не копируется с первичного endpoint.

Профильный provider output cap — 4000 токенов. Это параметр нового пути, а не
изменение production-модели или её конфигурации. `incomplete`/обрыв ответа не
вызывает продолжение, второй запрос или принятие частичного JSON. Лимит
должен пройти квалификацию с длинной историей до включения нового пути.

Перед приёмом истории и ответов нужна проверка соответствия действующему
согласию Ц1, публичной политике и принятой границе same-document script.
Переписка может содержать сведения третьих лиц. Спецификация не расширяет
действующее согласие и не утверждает новый privacy approval. Если потребуется
содержательное изменение текста согласия, оно должно быть отдельно утверждено
оператором с новой версией по [C1_CONSENT.md](C1_CONSENT.md).

Новые поля и результат не попадают в логи, ledger, browser storage или analytics.
Сохраняются существующие безопасные request ID, receipt и технические события.

## Синтетические сценарии приёмки

Все данные ниже вымышлены. Каждый сценарий превращается в полный fixture
с конкретным входом, ожидаемым outcome, `mustPreserveFacts` и `mustNotInvent`
до первого provider-вызова. Таблица задаёт содержание этих проверок.

| ID | Синтетическая ситуация | Обязательная гарантия |
| --- | --- | --- |
| `repeat-no-response` | В предыдущем обращении сообщено о неработающем светильнике. Ответ не получен, светильник по-прежнему не горит | Отсутствие полученного ответа не превращается в нарушение срока или отсутствие любых действий |
| `repeat-formal-response` | УО ответила «обращение принято в работу», сведений об осмотре и результате нет | Полученный формальный ответ не называется отсутствующим, работы не выдумываются |
| `repeat-partial-result` | Ранее сообщено о двух неработающих светильниках одного коридора. Один восстановлен, второй не горит | Частичный результат сохраняется, не утверждается полное бездействие |
| `repeat-inspection-only` | Пользователь сообщает об осмотре вентиляционного канала, но не знает его результата | Осмотр сохраняется как факт, результаты замеров и установленная причина не придумываются |
| `repeat-reported-resolution` | УО пишет об устранении течи. Пользователь после ответа наблюдает новое намокание в том же месте | Сообщение УО отделено от наблюдения пользователя, ложность ответа не устанавливается |
| `repeat-new-facts` | После первого обращения о не закрывающейся двери стало труднее пройти с коляской | Новое обстоятельство сохранено без придуманной травмы, аварии и технической причины |
| `repeat-emotional-partial` | Пользователь пишет «ничего не сделали», но также сообщает, что УО отрегулировала одну створку, а вторая не закрывается | Конкретный частичный результат не теряется ради эмоционального обобщения |
| `repeat-unknown-metadata` | Известны содержание прежнего обращения и сохраняющаяся проблема, номер/дата неизвестны, статус ответа `unknown` | Документ возможен без реквизитов, неизвестный ответ не превращается в неполученный |
| `repeat-long-history` | Одна проблема, последовательность осмотра и частичного устранения, отрицание предложенного ремонта, новое связанное проявление | Существенные этапы, условия и отрицания сохраняются без усечения, полный body проходит лимит |
| `repeat-unrelated-issues` | В одной истории объединены не связанная с дверью неисправность освещения и вывоз отходов | `multiple_issues`, без частичного повторного обращения |
| `repeat-conflicting-history` | В истории прямо сказано, что ответ получен и приведён, но пользователь выбрал `not_received` | `insufficient_history`, версия не выбирается за пользователя |
| `repeat-explicit-actions` | Пользователь просит сначала сообщить результат осмотра и не заменять исправную дверь | Явное требование сохранено backend целиком, автоматического пункта рядом нет |

Для `repeat-long-history` нужен отдельный offline boundary fixture с суммой
входа 7000 и проверкой отказа на 7001. Это техническая граница, не попытка
доказать семантическую полноту счётчиком символов. Invalid date, отсутствие
обязательного поля и несовместимые поля `response` проверяются до provider.

## Доказательства готовности и порядок реализации

[#319](https://github.com/ashikov/uo-request-generator/issues/319) реализует отдельные core-схемы, материализатор,
renderer и deterministic regression tests. Он не подключает provider/HTTP/UI,
не делает платных вызовов и не объявляет профиль рабочим. Проверяются точные
реквизиты, все статусы ответа, одно явное/автоматическое требование, строгие
схемы, полная длина результата и отсутствие усечения.

[#320](https://github.com/ashikov/uo-request-generator/issues/320) добавляет один provider-вызов нового профиля, parser и evaluation
path с production parity. Сначала проходят offline проверки всех fixtures.
До платного запуска фиксируются clean SHA, hashes prompt/schema, полный состав
12 сценариев, production-compatible модель/configuration class, pricing snapshot
и верхняя смета. Используется существующий benchmark, а не отдельный runner.
Разрешение расходов берётся из действующего поручения, а не из #234 или #307.
Если обязательный gate не помещается в оставшийся общий бюджет, итог INCOMPLETE.

Обязательный live gate — по одному ответу всех 12 сценариев и затем по одному
дополнительному ответу `repeat-partial-result`, `repeat-emotional-partial` и
`repeat-reported-resolution`. Итого максимум 15 attempts без retry ради удачи.
Каждый готовый документ целиком проходит независимый semantic review до
следующего вызова. Классы критической ошибки, стилистического недостатка
и недостаточного evidence применяются по
[LLM_BENCHMARK.md](LLM_BENCHMARK.md). Метрики полезного обогащения и исторические
разрешения #234 к новому профилю не переносятся. Первый подтверждённый
критический дефект останавливает gate. `REVIEW_NEEDED` приостанавливает следующие
вызовы до независимого разбора. Любой незавершённый обязательный слот оставляет
gate неполным.

Приёмка требует правильного outcome каждого сценария, отсутствия потерь
существенных фактов и домыслов, сохранения атрибуции и явных действий, а также
пригодности каждого успешного документа без существенной смысловой переработки.
Несколько удачных примеров не заменяют gate. Неуспешный профиль остаётся
недоступным, дальнейший кандидат требует отдельного ограниченного решения.

[#321](https://github.com/ashikov/uo-request-generator/issues/321) подключает HTTP/UI после успешной квалификации и закрытия правовой
и privacy-проверки. Сквозные offline/browser tests проверяют явный профиль,
общие safeguards, ошибки, копирование и отсутствие регрессии primary endpoint.
Новые нормативные или privacy-формулировки не принимаются разработчиком молча.

После каждого среза обязательны `make lint-md`, `pnpm check`, `git diff --check`
и независимое review фактического diff. Epic #195 закрывается только после
проверенного сквозного результата. Проектирование жалобы #176 использует
фактический стабилизированный контракт, а не будущий универсальный workflow.
