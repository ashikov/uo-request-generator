Итог: [NO-GO кандидата](RESULT.md), первый critical остановил диагностику.
До live статус был NOT DEMONSTRATED. Это отдельная гипотеза исправления фактов,
не возобновление обогащения #307 и не квалификация старого кандидата #320.
Production остаётся на одном вызове. Merge и deployment не разрешены.

## Гипотеза и границы

Один дополнительный вызов с полным исходным вводом и checked draft способен
минимально исправить существенные смысловые ошибки, не испортив корректный
документ. Самооценка модели не доказывает эту гипотезу.

В эксперименте первичной заявки строгий ответ содержит `status` и `draft`:
`unchanged` и `rejected` требуют `draft: null`, `corrected` требует полный
строгий generated draft. `unchanged` сохраняет исходный checked draft.
Изменять `subject` запрещено. Backend снова валидирует, материализует и собирает
документ, сохраняя исходные desiredActions и нормативные блоки.
Ошибки, отказ и невалидный результат не дают fallback-документ.

Модель не выбирает нормы и реквизиты. Проверка происхождения subject остаётся
прежней и не доказывает его смысловую применимость. Исходный неверный subject
не исправляется этим прототипом. Свободное стилистическое переписывание запрещено
prompt, но структурный parser не может доказать минимальность правки.

## Замороженная диагностика

Порядок в primary-cases.json: emotional-participant-mutation,
correct-lighting-control, working-door-negation-mutation,
conditional-actions-control. Первые и третьи drafts содержат намеренные ошибки,
второй и четвёртый — корректные controls. Anchors и запреты заданы до outputs.
Все четыре относятся к development/regression, не к независимому holdout.

После каждого единственного ответа отдельный reviewer сопоставляет input,
исходный draft, ответ и весь документ. Категории: исправлено, пропущено, новая
ошибка, корректный сохранён, безопасный отказ. Первый critical останавливает
кандидата. Ошибка provider/валидации оставляет диагностику INCOMPLETE без retry.
Review needed приостанавливает следующий dispatch до разрешения неоднозначности.
Отказ не считается исправлением, JSON success не считается semantic PASS.

Четырёх случаев недостаточно для GO: отдельно не проверены атрибуция,
причинность, предположения, неустранимое противоречие, длинный ввод и repeat.
При положительном сигнале следующий срез — replay повторного обращения и полный
неизменный qualification snapshot. Для первичного профиля сохраняются все
критерии #234 и его 43 слота, для повторного — 15 слотов #320. Известные failures
остаются regression, а не новым holdout. Final outputs не используются для tuning.
Перед полной квалификацией отдельно проверяются её approval и точная стоимость
в остатке. Неполный gate не даёт GO. Один адресный fix-pass возможен только при
конкретной исправимой причине, новой версии и достаточном бюджете.

синтетические данные и дополняет прежний учёт, не заменяет его.

Точный SHA, hashes и план сохраняются в каждой попытке. Отдельное approval
точного SHA из раздела #307 относится к той завершённой инициативе, а новую
ограниченную диагностику #328 явно разрешил владелец. Технические gates runner
сохранены. Полная primary qualification требует отдельной проверки этого правила.

## Условная runtime-интеграция

До GO никаких runtime Tasks и подключения нет. При GO потребуются отдельные
Tasks: два расходующих budget вызова, общий concurrency, timeout/cancel без retry,
измерение полной latency и проверка повторной передачи данных по Ц1/политике.
Требуемое решение оператора не может быть принято агентом. Repeat сохраняет
самостоятельные normative/privacy gates #321. Новые сервисы и БД не нужны.
