# Предлагаемый live gate кандидата B

Статус: **не запущен, требуется отдельное явное разрешение владельца**.
Связь: #267 и [proposed ADR-0005](../adr/0005-request-item-normalization-experiment.md).
Offline PASS не означает semantic PASS и не разрешает merge, Ready или rollout.
Квалификация A из #206 и завершённые #233, #244, #229, PR #246/#249 сохраняют
историческое значение, но не квалифицируют изменённые prompt и schema B.

## Сценарии и предел запросов

Одна текущая модель YandexGPT 5.1 Pro, Responses, `maxOutputTokens: 4000`.
Модель, транспорт и остальные настройки не меняются ради качества кандидата.
Все входы и смысловые ожидания находятся в едином синтетическом
[корпусе](../../packages/core/tests/fixtures.ts). Каждый ответ проверяется целиком:
`requestItem`, `problem`, `impact`, `subject`, warnings, outcome, `title`,
`circumstances`, итоговый `body` и выбор нормативного модуля.

| Scenario ID | Проверяемый риск | Всего попыток |
| --- | --- | ---: |
| `request-item-emotional` | Эмоции без добавления способа ремонта | 1 |
| `request-item-conditional-repair` | Проверка крыши и условное устранение | 3 |
| `request-item-inspection-only` | Только осмотр, пока без ремонта | 3 |
| `request-item-no-replacement` | Запрет замены, только регулировка | 3 |
| `request-item-cleaning-working-door` | Уборка исправного объекта без ремонта | 3 |
| `request-item-generic` | Общая просьба без конкретизации | 1 |
| `request-item-diagnosis-only` | Диагностика без автоматического ремонта | 3 |
| `request-item-explicit-component` | Заданный узел не становится доказанной причиной | 3 |
| `request-item-compound-constraints` | Последовательность, ограничения, предположительность | 3 |
| `request-item-contradictory` | Противоречие без выбора стороны за пользователя | 3 |
| `only-description` | Generic fallback и прежний риск технического домысла | 1 |
| `lighting-elevator-cabin` | Граница предметов освещения и лифта | 1 |
| `cleaning-entrance-door-mistaken-door-confirmation` | Ошибочное подтверждение, legal gate fail closed | 1 |
| `multiple-issues` | Отдельный outcome для несвязанных проблем | 1 |
| `impact-subject-explicit-group` | Явные последствия и участники | 1 |
| `ambiguous-location` | Несколько мест и сохранение structured location | 1 |

Итого: **16 сценариев, максимум 32 provider requests**. Десять новых сценариев
получают 26 попыток, шесть существующих controls — 6. Восемь критических
сценариев получают по два дополнительных повтора из-за риска потери запрета,
условия, модальности или появления ремонта. Это конечный объём эксперимента,
а не автоматическое начало общего prompt-tuning цикла.

## Порядок и остановка

1. Зафиксировать чистый exact HEAD Draft PR, актуальные prompt/schema hashes,
   локальную конфигурацию и новый pricing snapshot без публикации identifiers.
2. Получить отдельное явное разрешение владельца на эту матрицу и бюджет.
3. Выполнить по одной попытке `request-item-conditional-repair`,
   `request-item-inspection-only`, `request-item-no-replacement` и
   `request-item-diagnosis-only`. После каждого ответа провести независимый
   semantic review до следующего запроса.
4. При отсутствии blocker выполнить по одной попытке остальных 12 сценариев,
   также с review после каждого ответа.
5. Только после успешной первой волны выполнить по два дополнительных повтора
   восьми критических сценариев из таблицы. Каждый повтор проверяется до
   следующего вызова. Всего дополнительных попыток — 16.

Для каждого отдельного ответа использовать существующий runner с одним selector,
`--repeats 1` и интерактивным `RUN 1`. Обычная команда ниже показывает только план:

```bash
pnpm benchmark:llm -- --config .llm-benchmark.local.json \
  --scenario request-item-conditional-repair --repeats 1
```

Добавлять `--run` можно только после отдельного разрешения. Не запускать одним
пакетом `--repeats 3`: runner не умеет самостоятельно останавливать вызовы по
смысловому verdict. Внешний порядок «один ответ → review → следующий ответ»
обязателен. Retry, второй вызов для улучшения ответа, LLM-as-a-judge и смена
модели запрещены.

Любая потеря отрицания, его области, условия, ограничения `только`, `пока`,
`после`, `без`, `если`, `при необходимости` или пользовательской модальности —
semantic blocker. То же относится к новому самостоятельному действию, ремонту,
неподтверждённому узлу, причине, способу, исполнителю или требованию, превращению
диагностики в ремонт и существенной регрессии соседнего prose, subject, legal
gate, location либо `multiple_issues` относительно действующих expectations.
Один unsafe repeat нельзя компенсировать удачными повторами.

На blocker остановить весь gate и предложить отклонить B, сохранив A.
Не закрывать PR автоматически без решения владельца. Не начинать новый цикл
настройки prompt. Ошибка транспорта, provider, валидации, hard checks,
превышение бюджета или `REVIEW_NEEDED` также останавливают дальнейшие запросы
без retry: доказательств для допуска недостаточно.

`requestItem: null` при наличии `desiredActions` — разрешённый abstention,
который сохраняет исходный текст через A. Учитывать число abstentions отдельно
от строк, сохранивших смысл. Безопасный fallback сам по себе не доказывает
пользовательскую пользу B. Стилистические вариации без изменения смысла не
являются регрессией, единственная литературная формулировка не требуется.

## Pricing snapshot и верхняя оценка

Снимок публичной [тарификации Yandex AI Studio](https://aistudio.yandex.ru/ru/docs/ai-studio/pricing)
проверен 09.09.2026 без inference: синхронный YandexGPT Pro 5.1 — **800 ₽ за
миллион входящих и 800 ₽ за миллион исходящих токенов, с НДС**.
Максимум выходящей части одного запроса при 4000 токенов — 3,20 ₽.

Смета рассчитана бесплатно через существующую чистую функцию
`createBenchmarkPlan`, без создания gateway, чтения `.env`, ключей или закрытого
model ID. Использован синтетический ASCII model ID длиной 256 байт. Перед
live gate требуется подтвердить, что сериализованный реальный ID не длиннее
этого резерва, либо пересчитать смету. Остальное тело запроса формируется
текущими production prompt/schema и выбранными fixtures.

Принятое в runner консервативное правило — не более одного входного токена на
UTF-8 байт полного JSON request body. Полученные оценки входа: 26 073–26 540
для новых сценариев и до 42 122 для controls с subject. Это оценка расходов,
а не измеренный usage и не требование заполнить контекст модели. Она включает
служебный JSON и может существенно превышать фактическую токенизацию.

```text
стоимость запроса = (inputTokenUpperBound + 4000) × 800 / 1 000 000 ₽
максимальная оценка 32 попыток = 810,8728 ₽ с НДС
предлагаемый округлённый бюджет = 811 ₽ с НДС
```

При изменении HEAD, конфигурации, состава сценариев, цены или превышении резерва
длины ID смета требует пересчёта до вызовов. Нельзя увеличивать число попыток
или бюджет без отдельного разрешения. Для воспроизведения сметы использовать
`createBenchmarkPlan` с ценами 800/800, Responses, output cap 4000,
`model: "S".repeat(256)` и числом повторов из таблицы, затем сложить
`maximumCost` отдельных планов. Это не обращается к провайдеру.

## Решение после gate

Сохранить независимый verdict по каждому ответу, abstentions, существенные
quality findings и безопасные агрегаты. Не публиковать raw provider errors,
закрытые identifiers или инфраструктуру. Все отчётные примеры синтетические.

Даже полное прохождение этой матрицы не означает статистической гарантии и не
переносит автоматически историческую квалификацию A. Допуск B, достаточность
наблюдаемой пользы, согласование основной документации и принятие ADR требуют
отдельного решения владельца. До него PR остаётся Draft и не сливается.
