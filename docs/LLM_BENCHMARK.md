# Локальные live LLM regression evals и semantic review

Это канонический процесс проверки генеративных частей заявки на общем
синтетическом corpus. Он помогает отличить нестабильность модели от нарушения
продуктового контракта, но не выбирает production-модель автоматически и не
заменяет независимый semantic review.

Команда не входит в CI или `pnpm check`. Обычный запуск только показывает план
и выполняет ноль provider requests:

```bash
pnpm benchmark:llm -- --config .llm-benchmark.local.json
```

## Локальная конфигурация

Скопируйте `.llm-benchmark.example.json` в `.llm-benchmark.local.json` и
замените model IDs и синтетические цены. Локальный файл исключён из Git. В нём
явно задаются:

- protocol
- `maxOutputTokens` от 1 до 4000
- одна или несколько моделей с уникальными label и ID
- валюта и цены input/output за миллион токенов

Цены не встроены в код и не загружаются автоматически. Для каждого model ID
нужно явно указать обе цены. Значение `0` допустимо только как осознанно
заданная бесплатная цена.

Для Chat Completions дополнительно укажите поддерживаемый провайдером параметр:

```json
{
  "apiProtocol": "chat-completions",
  "chatCompletionsOutputTokenParameter": "max_tokens"
}
```

Вместо `max_tokens` можно выбрать `max_completion_tokens`. Без явного параметра
Chat Completions benchmark отклоняется до provider request. Responses API всегда
получает `max_output_tokens`.

API key в benchmark config не хранится. Только для явно подтверждённого запуска
нужны локальные `LLM_API_URL`, `LLM_API_KEY`, `LLM_AUTH_SCHEME` и
`LLM_PROVIDER`. Необязательный `LLM_FOLDER_ID` передаётся как существующий
provider header. Plan mode не читает ключ и работает без provider network
access, CAPTCHA, Fastify и deployment. `LLM_MODEL` не используется.

## Scenarios и повторы

Без selector используются все актуальные fixtures из
`packages/core/tests/fixtures.ts` в их исходном порядке. Число scenarios не
фиксируется в документации: перед qualification его вычисляют из текущего
corpus и сверяют с планом runner.

Короткий план ограничивается с начала списка:

```bash
pnpm benchmark:llm -- --config .llm-benchmark.local.json --limit 5
```

Конкретные scenarios выбираются повторяемым аргументом. Их порядок всё равно
определяется общим fixture-набором:

```bash
pnpm benchmark:llm -- --config .llm-benchmark.local.json \
  --scenario wording-normalization \
  --scenario minimum-sufficient-requests
```

`--scenario` и `--limit` несовместимы. Число повторов по умолчанию равно `1`,
максимум — `5`:

```bash
pnpm benchmark:llm -- --config .llm-benchmark.local.json --repeats 3
```

Запросы идут последовательно в порядке model → scenario → repeat. Общее
число равно `models × scenarios × repeats`. Shuffle, concurrency,
автоматические повторы, fallback и LLM-as-a-judge отсутствуют. Фактическое
число попыток никогда не превышает исходный план. План свыше 100 запросов
отклоняется до paid run.

Обычный scenario достаточно выполнить один раз. Для критического бывшего
regression case число повторов фиксируется до запуска. Для инициативы #234/#306/#307 действует план v0.3 ниже, остальные исторические gates не
создают для неё дополнительных квот. Один успешный ответ не доказывает устойчивость, если
другой repeat нарушает blocker-инвариант.

## Fixture contract

Corpus остаётся единым массивом `scenarios` в
`packages/core/tests/fixtures.ts`. Новый воспроизводимый смысловой дефект по
возможности получает полностью synthetic scenario в этом массиве, а не второй
benchmark.

Каждое ожидание относится к одной из трёх категорий:

- `blocker product invariant` — объективный публичный или safety-контракт,
  нарушение которого блокирует qualification
- `quality expectation` — смысловой критерий для независимого review, который
  нельзя надёжно доказать структурной проверкой
- `accepted beta limitation` — известное допустимое ограничение, которое само
  по себе не является regression

Hard expectations защищают только текущие инварианты: `outcome`, предупреждения,
`subject.kind`, выбор детерминированного нормативного модуля, ровно один
backend-owned `requestItems` и отсутствие выдуманного provider-требования.
Provider draft проходит тот же parser, materializer и renderer, что production.

Внутренний `subject.kind` проверяется как blocker только когда конкретный выбор
нужен для наблюдаемого продуктового или safety-инварианта. В обоих controls с
ошибочным подтверждением технического предмета при уборке допустимы cleaning
subject или `subject: null`: запрещены технический subject, предметный нормативный
модуль и выдуманный ремонт, а явное действие уборки должно сохраниться. Положительные
controls поддержанного предмета по-прежнему требуют соответствующие subject и модуль.

Безопасное дополнительное warning само по себе не блокирует qualification.
Жёсткое требование его отсутствия требует отдельного пользовательского или
safety-основания. Содержание предупреждений остаётся предметом проверки: они
не должны вводить домыслы, противоречить вводу или подменять факты в `body`.

Генеративные `title`, `problem`, `circumstances` и `impact` не закрепляются одной
эталонной фразой. Их полнота, естественность, сохранение фактов и отсутствие
домыслов относятся к quality expectations и semantic review.

Явный `desiredActions` должен целиком сохраниться в одном request item после
минимальной нормализации представления. Backend не добавляет рядом общий пункт.
Без `desiredActions` универсальный пункт из
[`REQUEST_RULES.md`](REQUEST_RULES.md#требование-первичной-заявки)
считается полноценным beta-результатом. Отсутствие автоматически созданных
этапов установления причины или проверки результата является accepted beta
limitation, а не regression.

Историческое ожидание, старый ADR, прежний provider output или удобство fixture
не создают продуктовый инвариант. Перед paid re-gate reviewer сверяет каждое
blocking expectation с текущими `docs/REQUEST_RULES.md` и ADR-0004. Устаревшее
ожидание сначала исправляют в corpus и документации. Его не подгоняют под
последний случайный ответ модели.

Исторические hard/semantic FAIL остаются результатами прежнего запуска.
После изменения acceptance сохранённые synthetic provider outputs оцениваются
отдельно по новому контракту, с указанием исходного запуска и версии исправлений.
Если provider prompt, schema, сериализация ввода и configuration class не
изменились, повторять provider calls только ради такого пересмотра не требуется.
Offline-переоценка не разрешает следующий платный этап автоматически.

Несколько мест могут относиться к одной проблеме. Structured `location` не
перекрывает место из `description` и сохраняется renderer по
[`REQUEST_RULES.md`](REQUEST_RULES.md#одна-проблема-в-заявке). Безопасный повтор
не является regression. Реальная неоднозначность остаётся quality
expectation и может быть выражена безопасным warning.

В `emotional` обобщение явно названных участников сложного `description`
относится к accepted beta limitation #229. Неисправность лифта и указанная
длительность должны сохраниться без ложной точности. Новые причины, повреждения,
выполненные работы, конкретный ремонт и другие независимые выдуманные факты
остаются blocker. Эта уступка не распространяется на отдельные participant
controls для явного `consequences`.

## План и платный запуск

Узкий контроль #224 использует два исторических синтетических ввода:
`description-fact-preservation` и `description-explicit-referent-preservation`.
Первый допускает опущение только неоднозначной связи, второй требует сохранить
явную связь верхнего этажа с пятым. Остальные факты, последствия и явное действие
сохраняются в копируемом тексте в обоих случаях. Смысл проверяется отдельно от
hard checks, безопасное предупреждение необязательно.

Результаты PR #225 (targeted 3/3 и broad 2/2 для каждого контроля) остаются
историческими: после #244 изменились prompt, provider schema, сериализация и
формирование требований. Вердикт переноса —
`HISTORICAL_EVIDENCE_RELEVANT_BUT_NOT_TRANSFERABLE`. Закрытый без merge PR #225
служит источником сценариев и исследования, но не базой текущей реализации.
Текущий gate требует сначала по одному ответу и смыслового review, затем только
при успехе ещё по два. Каждый следующий ответ проверяется до нового вызова.
Предел — шесть попыток без повторов после ошибки, иных сценариев или настройки
prompt. Provider/request failure оставляет результат неопределённым, смысловая
регрессия останавливает gate и оставляет #224 открытой.

До первого запроса plan mode показывает модели, scenarios, повторы, общее число
запросов, output cap, pricing snapshot, максимальную оценочную стоимость, путь
отчёта и безопасное состояние исходников. Состояние имеет только один из трёх
видов: `clean` с commit SHA, `dirty` с отдельными признаками tracked и untracked
изменений или `unavailable`. Пути файлов, raw porcelain, remotes и другие
сведения о локальном окружении не выводятся и не сохраняются.

Input оценивается консервативно как не более одного токена на байт полного
UTF-8 request body с production prompt и schema. Это верхняя оценка расходов, а
не точный provider billing.

Paid run допускается только при `clean` source state с доступным commit SHA. Он
требует одновременно `--run`, интерактивный stdin и точную фразу
`RUN <число запросов>` после вывода плана:

```bash
pnpm benchmark:llm -- --config .llm-benchmark.local.json --repeats 3 --run
```

Любой другой ответ отменяет запуск с нулём запросов. Non-TTY запуск также
отклоняется. Bypass-флагов нет. Текущий implementation pass и подготовка
qualification выполняются только в plan mode без `--run`.

## Отчёт и диагностика

После подтверждения Markdown-отчёт последовательно обновляется в
`.tmp/llm-benchmark/`. В нём сохраняются timestamp, clean commit SHA,
безопасные model labels, prompt hash, pricing snapshot, план, число выполненных
запросов, repeats, usage, latency, оценочная стоимость и hard PASS/FAIL summary.

Каждая выполненная попытка содержит безопасную диагностическую трассу. Она
показывает первый этап с отказом и уже пройденные этапы в порядке фактического
исполнения:

```text
network
→ http
→ provider_envelope
→ provider_status
→ output_extraction
→ json_parse
→ provider_wire_validation
→ canonical_validation
→ materialization
→ subject_legal_selection
→ renderer
→ hard_expectations
```

Gateway заполняет трассу до `renderer`. Benchmark runner добавляет
`hard_expectations`, потому что fixture contract не относится к production
gateway. Для `multiple_issues` трасса штатно завершается после
`canonical_validation`: materialization, выбор нормативного модуля и renderer к
этому исходу неприменимы. `firstFailureStage` всегда указывает первый этап со
статусом `FAIL`.

После единственного `JSON.parse` structural probe извлекает только JSON-тип
корня, наличие и JSON-тип `draft`, наличие известных полей, число неизвестных
полей без их имён и известный `outcome`. Probe не принимает ответ и не ослабляет
строгую валидацию. Диагностика ошибок валидации содержит только разрешённый код,
санитизированный путь, ожидаемую JSON-категорию и число ошибок. Полное сообщение,
отклонённое значение и произвольное имя поля не сохраняются.

Materialization сообщает только `PASS` или `FAIL`. В диагностике нет прежних
причин распределения, процедурных ролей, source fragments или location.

Usage имеет три состояния: `available`, `missing` и `invalid`. Числа токенов
сохраняются только для `available` и берутся из provider usage. Оценка по длине
текста не выполняется.

Для каждого scenario/repeat отчёт включает category, issue provenance,
synthetic input, локально проверенный provider draft, материализованный
`PrimaryRequestDraft`, deterministic observations, rendered result или
контролируемую ошибку, hard expectations, quality expectations и accepted beta
limitations. Для generated-ветки сохраняется безопасный status выбора
предметного модуля. Для `multiple_issues` сохраняется только канонический
`outcome`.

Model IDs, API URL, auth headers, credentials, raw provider response, реальные
пользовательские данные и production infrastructure в отчёт не попадают.
Диагностика не содержит пользовательские или provider-authored значения. Для
неуспешного Responses-result допускаются только внутренний `failureStatus`,
проверенный `status`, категория наличия кода ошибки `known`, `unknown` или
`missing`, разрешённый `error.code` для категории `known` и проверенный
`incomplete_details.reason`. Неизвестное исходное значение `error.code`,
`error.message` и сырой provider envelope не сохраняются.

Repeat-сводка различает ошибки выполненного запроса и недоступность provider.
Не начатые после такого отказа запросы показываются отдельно и не считаются
новыми attempts или semantic failures. Неполный запуск остаётся fail closed.

Если usage отсутствует, запрос и результат сохраняются, а usage и стоимость
отмечаются как `unavailable`. Значения по длине ответа не выдумываются.

Ошибка конкретного request фиксируется без retry. HTTP 400, 404 и 422,
незавершённый Responses-result и локальная ошибка валидации не повторяются.
Сетевая ошибка, timeout, HTTP 401, 403, 429, 5xx и другие provider failures
пропускают остаток текущей model group. Multi-model plan после этого переходит
к следующей модели. `SIGINT`, `SIGTERM` и ошибка обязательной записи report
останавливают весь run.

Успешный exit code означает только прохождение объективных hard checks. Он не
доказывает смысловую корректность генеративного текста.

## Совместимость provider response schema

Provider response содержит только `outcome`, `title`, `problem`,
`circumstances`, `impact`, `subject` и `warnings`. В нём нет поля требований,
технического ремонта, процедурных ролей или селекторов исходных фрагментов.

До qualification offline-проверка должна подтвердить:

```text
одинаковый confirmedProblemSubject
+ одинаковый прочий контекст схемы
→ одинаковый SHA-256 JSON Schema при наличии и отсутствии desiredActions
```

Измерения прежних вложенных схем, отдельные A/B-пробы и исторические hash не
являются текущим acceptance criterion. Новый provider output field допустим
только при конкретной пользовательской пользе и отдельном продуктовом решении.

## Semantic review

Reviewer отдельно оценивает каждый scenario/repeat:

- сохранены ли явные факты, место, длительность, масштаб и субъект
- не добавлены ли новые причины, повреждения, люди, события и произошедший ущерб
- не появился ли неподтверждённый конкретный ремонт
- сохранены ли последствия и желаемые действия без противоречия
- уместен ли безопасный выведенный impact
- не превращён ли потенциальный риск в установленный факт
- не раздут ли простой дефект необязательной конкретикой
- не объединены ли несколько несвязанных проблем
- соответствует ли `subject` фактической проблеме
- согласован ли descriptive prose с deterministic legal/result layer
- нет ли существенного смыслового повтора между описательными полями
- сохраняется ли один смысл при разных естественных формулировках repeats

Классификация review:

- `PASS` — semantic contract соблюдён
- `REGRESSION` — нарушен актуальный scenario contract
- `UNSTABLE` — repeats дают противоречивый результат
- `REVIEW_NEEDED` — evidence недостаточно для уверенной оценки

Стилистическое отличие и меньшая специфичность безопасного общего результата
сами по себе не являются regression. LLM output не используется для проверки
юридической корректности законодательства.

Если semantic defect становится надёжно формализуемым, fixture получает hard
expectation только при наличии текущего продуктового основания. При возможности
добавляется обычный deterministic regression test.

### Рубрика качества

Reviewer оценивает исходный synthetic input, checked provider draft,
материализованный draft, весь `title`/`body`/`warnings`, нормативный модуль и
единственный пункт `Прошу:`. Hard PASS необходим, но недостаточен. Смысловые
blockers остаются blockers, даже если не выражены автоматической проверкой.

В таблице «пример класса» демонстрирует именно этот класс, «контрпример» —
границу с другим классом. Все примеры синтетические, формулировки не эталонные.

| Класс | Проверяемый признак | Пример класса | Контрпример |
| --- | --- | --- | --- |
| Критическая ошибка | Потерян или искажён существенный факт, отрицание, условие, требование. Добавлены событие, причина, узел, ремонт, люди, ущерб или неподходящее нормативное основание. Нарушен обязательный safety/privacy-контракт | Ввод: «Лифт шумит, но работает». Вывод: «Лифт остановился, требуется замена привода». «Возможна неисправность привода» также выдумывает узел | «Сильный шум снижает комфорт поездки» не утверждает остановку или причину |
| Некритичная ошибка обогащения | Лишний или слабо обоснованный общий вывод, без нового факта и изменения смысла требования | К отметине неизвестной природы добавлено «Ситуация может создавать общие неудобства» без объяснимой практической связи | «Отметина появилась после взлома» — критическая ошибка. «Ограничена видимость прохода» при отсутствии света — полезный вывод |
| Полезное обогащение | Конкретное практическое значение или непосредственно обоснованный потенциальный риск сверх переданных смыслов. Нет скрытых допущений | Нет света на лестничной площадке → «Это ограничивает видимость прохода». Открыт вход с улицы → «Возможен посторонний доступ» | «Необходимо обратить внимание», пересказ «Свет не работает» или повтор явного `consequences` не добавляют пользы |
| Корректное воздержание | По заранее оценённому вводу нет безопасного основания для добавки. Факты сохранены, необоснованного вывода нет | Неизвестная отметина без сведений о функции двери → описание без выведенного риска, `impact: null` | Отсутствие вывода об ограниченной видимости при неработающем свете допустимо в beta, но для v0.3 это упущенная возможность, а не успешное воздержание |
| Стилистический недостаток | Факты и обязательный смысл сохранены, неудачна только форма | При неисправном лифте сохранено «Приходится подниматься вручную» | «Приходится пользоваться работающим лифтом» меняет смысл и является критической ошибкой |
| Недостаточно evidence | Нет полного входа, результата или ясного основания для уверенного смыслового verdict. Это `REVIEW_NEEDED` | Доступен только заголовок, нет body и исходного условия требования. Либо reviewers не разрешили смысловое расхождение | Полный текст с явной выдуманной кражей даёт критический verdict. Неизвестная причина во входе сама по себе не мешает оценить корректное воздержание |

Критические ошибки не входят в допустимые 5%. Возможность удалить предложение
не понижает severity. Утрата существенного факта об исправности объекта,
превращение пользовательского риска в событие или условия в безусловное действие
критичны. Узкая beta-уступка об участниках в `emotional` не переносится на v0.3
и не расширяется на явные `consequences`.

Классы — отдельные признаки review, без нового provider-поля или системы
вердиктов. Одна заявка может содержать полезный вывод, некритичную ошибку и
стилистическое замечание одновременно. Критическая ошибка имеет приоритет,
подтверждённые дефекты сохраняются даже при дополнительном `REVIEW_NEEDED`.
Полезность не засчитывается для заявки с критической ошибкой. Пропуск полезного
вывода в подходящем случае уменьшает полезность, но сам по себе не увеличивает
число ошибок обогащения. Формально непустая, но бессодержательная добавка не
даёт полезности и оценивается как некритичная ошибка, если это лишний общий вывод.

Существующие verdict используются так: `REGRESSION` для нарушения актуального
обязательного контракта, `PASS` для его соблюдения, `REVIEW_NEEDED` при
неразрешённой оценке. Дополнительно записываются классы из таблицы. `PASS` одного
ответа со стилистическим замечанием не означает PASS квалификации кандидата.
`UNSTABLE` — признак сценария при расхождении repeats по сохранению смысла,
severity, полезности, abstention или subject/legal selection. Литературная
вариативность без этих различий не является неустойчивостью. Все repeat-verdict
показываются отдельно, успешный ответ не отменяет критический в другом repeat.

### Решение по историческим expectations

| Случай | Beta: текущая классификация | Цель v0.3 |
| --- | --- | --- |
| `impact-natural-lift-consequence`, неестественное «подниматься вручную» | Quality expectation естественности, при сохранённом смысле стилистический недостаток. Потеря явно переданного последствия или новые люди остаются blocker | Та же граница. Предпочтительна естественная нормализация без единственной обязательной фразы |
| `only-description`, нет практического значения отсутствия света | Accepted beta limitation: выведенный `impact` необязателен | Quality expectation полезного вывода об ограниченной видимости. Отсутствие уменьшает долю полезности, не становится критической ошибкой |
| Незакрывающаяся дверь, нет потенциального риска | Accepted beta limitation отсутствия выведенного `impact`. `wording-normalization` описывает дверь общего помещения и не доказывает открытый вход с улицы | Quality expectation риска доступа только при непосредственном основании. Новый `entrance-door-unconfirmed` явно задаёт открытый вход. Выдуманные проникновение, кража и неисправный замок — blocker |

Эти решения не исправляют прошлые FAIL на PASS. При переоценке создаётся новый
разбор с исходным run, SHA, версией контракта и причиной новой классификации.
Историческое качество не доказывает достижение v0.3. Пример уместного «вручную»
в `impact-natural-manual-door-operation` сохраняет защиту от механической замены.

### Корпус и предварительный отбор

При подготовке #234 исходный корпус содержал **35 сценариев**: 34 `generated`

### Единицы наблюдения и расчёт

Каждый кандидат имеет отдельную сводку с полным списком запланированных слотов
`scenario × repeat`, фактических attempts и пропусков. Кандидат — зафиксированная
версия prompt/schema, входной сериализации, модели/configuration class и
детерминированного кода. Финальный кандидат включает #306 и #307. Изменение,
способное повлиять на смысл, образует новую версию и не наследует успешные ответы
другой версии. Финальная проверка неизменного кандидата не новый кандидат.

План qualification ниже — 39 первых ответов и четыре дополнительных repeat,
всего 43 слота. Из них 42 слота ожидают готовую заявку, один — `multiple_issues`.
F содержит 15 первых ответов и четыре repeat, всего 19 готовых заявок. Отдельно
проверяются весь corpus и независимый F. Для итогового PASS пороги выполняются
на обоих срезах, а coverage и критические инварианты — на всех 43 слотах.

| Метрика | Единица, числитель и знаменатель | Условие |
| --- | --- | --- |
| Критические ошибки | Один ответ любого outcome с хотя бы одной критической ошибкой. C — число таких ответов, A — все запланированные ответы | C = 0 при полной оценке A/A. Любая обнаруженная ошибка блокирует независимо от процентов |
| Некритичные ошибки обогащения | Одна готовая заявка одного repeat. E — число заявок хотя бы с одной такой ошибкой, G — все запланированные и оценённые готовые заявки | E/G ≤ 0,05. Несколько ошибок одной заявки считают один раз |
| Полезность | Один заранее подходящий сценарий. U — сценарии с полезным обогащением во всех запланированных repeats без критических ошибок, K — все заранее подходящие сценарии | U/K ≥ 0,80. Repeat не увеличивает K |
| Ручная приёмка | Один первый документ каждого из 15 F. M — документы без существенной смысловой переработки, знаменатель всегда 15 | M ≥ 12, 0 критических ошибок. Repeat не заменяет первый документ |

Считают по целым числам: `20 × E ≤ G`, `5 × U ≥ 4 × K`.
Допустимо максимум `floor(G/20)` ошибок и нужно минимум `ceil(4K/5)` полезных
сценариев. В данном плане для всего corpus E ≤ 2 при G = 42 и U ≥ 9 при K = 11.
Для независимого F E = 0 при G = 19 и U ≥ 4 при K = 5. При G < 20 одна ошибка
уже превышает 5%. Например, 1/19 = 5,26% не проходит, 1/20 = 5% проходит.
Показывают дробь и процент до двух знаков, решение принимают по точной дроби,
а не округлённому проценту. При нулевом знаменателе метрика `unavailable`,
не PASS.

Отсутствующий вывод (`impact: null` либо только пересказ) не увеличивает U.
В подходящем сценарии он остаётся в K. В неподходящем случае отсутствие
добавки — корректное воздержание, не ошибка и не полезное обогащение. `impact`
с переданными последствиями не обязан быть null: проверяется отсутствие
необоснованной добавки, а не заполненность поля. Если полезный смысл естественно
выражен в другом описательном поле, оценивается весь документ, без требования
нового поля или фиксированной фразы.

Повторы считаются отдельными заявками для E/G и C, но не независимыми
сценариями для U/K. Для каждого повторяемого сценария показывают все verdict,
частоту полезных ответов `u/r` и расхождения по фактам, рискам, требованиям и
subject/legal selection. Различие полезности даёт `UNSTABLE` и не засчитывает
сценарий в U, даже если один ответ полезен. Некритичная неустойчивость сама по
себе не заменяет числовые критерии. Критическая ошибка в любом repeat всегда
FAIL всего кандидата.

Provider, transport, validation и materialization failures показывают отдельно
по диагностическому этапу. Начатый вызов считается attempt и расходует бюджет
даже без результата. Не начатые слоты — `not attempted`, не новые attempts.
Неожиданный outcome, например `multiple_issues` вместо одной проблемы,
не исключает сценарий: это нарушение контракта. Правильный `multiple_issues`
проверяется на correctness и входит в coverage, но заранее не входит в G/K
и 15 документов. Неудачи и `REVIEW_NEEDED` не превращаются в semantic PASS.

До заполнения всех слотов и разрешения всех смысловых verdict сводка только
предварительная: отдельно показывают planned/attempted/valid/reviewed и
число пропущенных, отказавших и неразрешённых оценок. G не подменяется удобным
подмножеством удачных ответов. Недоступный ответ не объявляется смысловой
ошибкой без evidence, но gate остаётся INCOMPLETE и не может стать PASS.
Исключения для улучшения процентов, выбор лучших repeats и объединение
кандидатов запрещены. Резерв не даёт разрешения повторять ошибку ради удачи.

Ручной reviewer получает 15 первых готовых документов F, входы и правила.
«Без существенной смысловой переработки» означает возможность подать заявку,
не восстанавливая факты/условия, не удаляя домыслы и не переписывая требования
или нормативное основание. Коррекция пунктуации и необязательного стиля допустима.
Для каждого документа фиксируют пригодность и причину. Отсутствие нужной
содержательности может сделать документ непригодным даже без критической ошибки.
Три допустимых непригодных документа не разрешают ни одной критической ошибки.
Неполные 15 документов не дают PASS и не заменяются успешными repeats.

### Отчёт и ограничения выводов

Используется существующий Markdown-отчёт benchmark в ignored-каталоге. К нему
добавляют ручной разбор, не новую систему хранения. В разборе фиксируют:

- версию контракта #234, SHA кандидата и отчёта, hashes prompt/schema с descriptions
- замороженные D/F/R, eligibility, запланированные repeats и порядок вызовов
- для каждого ответа hard verdict, semantic verdict, классы, основание и reviewer
- для каждого сценария все repeats и `UNSTABLE`, без выбора лучшего
- C/A, E/G, U/K, M/15, coverage и failures, итог PASS/FAIL/INCOMPLETE
- те же raw counts по `scenario.category`, по каждому `confirmedProblemSubject` и отдельно без подтверждённой категории
- накопленные attempts, стоимость по usage, неизвестные расходы и консервативный остаток

Группы с нулевым K показывают `unavailable`, без выдуманного процента. Общий
процент не доказывает качество каждой категории. Малые группы показывают
описательно, без утверждения статистической устойчивости. Приёмка проверяет
готовый документ целиком, а не только `impact`.

5% — допуск на этой определённой synthetic test sample, **не доказанная частота
ошибок в реальном пользовательском потоке**. Отбор целевой, выборка мала,
repeats коррелированы. Ноль обнаруженных ошибок не означает нулевой риск.
Нельзя интерпретировать повторяемые ответы или проверенные 15 документов как
случайную репрезентативную выборку пользователей либо заявлять доверительную
границу частоты ошибок без отдельного исследования. Сводки beta и v0.3,
baseline и разных кандидатов не объединяются.

### План экспериментов #307 и общий бюджет

Общий предел инициативы #234/#306/#307 — baseline плюс максимум два проверяемых
кандидата, **80 provider attempts и 2500 ₽**. Ошибки, repeats, qualification и
ручная приёмка входят в эти пределы. Новая ветка, issue или название гипотезы
не обнуляют учёт. Исторические результаты до инициативы можно переиспользовать
офлайн, но нельзя выдавать их за новые независимые ответы финального кандидата.
В #234 provider requests = 0 и расходы = 0 ₽.

Сначала offline: обязательные проверки всего corpus, schema/parser/materializer/
renderer, production/evaluation parity и review пригодных сохранённых synthetic
outputs. В локальных исторических отчётах есть checked drafts и rendered result,
включая RUN 12 из раздела #206 ниже. Это материал для переоценки, не готовая
квалификация v0.3. Перенос подтверждается сравнением фактических prompt,
schema/descriptions, сериализации входа, parser и configuration class с точным
SHA исходного запуска. Нужны полный synthetic input, checked draft и проверка
полноты отчёта. Отсутствие одного из этих оснований означает только историческое
evidence, не переносимый baseline. Разница output cap 1200/4000 разрешена лишь
в узком историческом решении #229, а не для любых новых кандидатов.

В текущей реализации #306 изменён только универсальный fallback. Предметные
шаблоны не включены из-за отсутствия доказуемой смысловой применимости.
Offline-тесты подтверждают детерминированные границы, а не завершение всей #306
или достижение метрик v0.3. Provider prompt, schema/descriptions и лимиты
сохранены. Провайдерные вызовы и расходы при этой реализации равны нулю.

Если в #306 меняется только детерминированный слой, неизменный сохранённый
provider draft можно заново провести через актуальные materializer/renderer и
оценить новый документ офлайн. Этот разбор не доказывает генеративную устойчивость
и не даёт оплаченных попыток сверх общего лимита. При изменении prompt/schema
старые ответы не являются ответами нового кандидата. F не просматривается для
настройки даже при переоценке сохранённых outputs.

Baseline фиксируется после стабилизации #306, до изменения prose-инструкций #307. Так различие требований не смешивается с эффектом обогащения. Первый
кандидат проверяет одну гипотезу: явное требование непосредственно полезного
вывода с abstention при недостаточном основании. Второй слот — либо заранее
обоснованная альтернативная гипотеза, либо единственный адресный fix-pass после
разбора дефекта первого. Это всего два слота, не два плюс бесплатное исправление.
Любая платно проверенная смысловая версия занимает слот. Между development и
qualification выбранная интегрированная версия не меняется.

| Этап | Максимум attempts | Денежный резерв, ₽ | Набор и условие перехода |
| --- | ---: | ---: | --- |
| Offline и переносимость | 0 | 0 | Полный corpus, историческое evidence и обязательные проверки |
| Baseline | 8 | 200 | По одному ответу каждого D, меньше при доказанном переносе |
| Кандидат 1 | 8 | 200 | Те же D, review каждого ответа до следующего |
| Кандидат 2, если необходим | 8 | 200 | Те же D, одна альтернатива либо один fix-pass |
| Финальный интегрированный gate | 39 | 1100 | Весь corpus по одному разу, включая 15 F для ручной приёмки |
| Критические повторы финального gate | 4 | 150 | По одному дополнительному ответу четырёх ID ниже |
| Нераспределённый аварийный резерв | 13 | 650 | Только заранее конкретизированные проверки, без третьего кандидата и retry ради удачи |
| Итого потолок | 80 | 2500 | Остаток не является заданием потратить его |

Четыре критических repeat: `working-elevator-noise` (работа против остановки),
`desired-actions-conditional-door` (условия и запрет),
`cleaning-entrance-door-mistaken-door-confirmation` (исправность и неверная
категория), `description-explicit-referent-preservation` (однозначная связь).
Финальный run каждого ID содержит первый ответ и один repeat. При подтверждённом
blocker повтор не выполняется. Резерв 13 не нужен для штатных 67 attempts и
не увеличивает ни число кандидатов, ни количество безусловно разрешённых вызовов.
Дополнительные проверки из резерва задаются до получения соответствующих outputs,
включаются в denominators и требуют отдельного согласования. Они не заменяют
неудавшиеся обязательные слоты. Если полный gate не помещается, итог INCOMPLETE.

Денежные суммы — плановые резервы внутри аварийного потолка, не актуальные
тарифы и не разрешение потратить. Перед первым вызовом нужны реальные цены и
верхняя смета всех оставшихся этапов, включая финальные 43 ответа. Если смета
не помещается в остаток, платный этап не начинается. Перераспределение резерва
фиксируется до этапа и не увеличивает общие пределы. 2500 ₽ — аварийный потолок,
не целевой расход. Около 500 ₽ накопленного расхода владелец отдельно оценивает
пользу продолжения по эффекту D, blockers и оставшемуся финальному бюджету.
Проверку проводят перед следующим вызовом, который приблизит расход к этой
отметке или пересечёт её. Это не новая автоматическая квота в 500 ₽.

Attempts считают с момента передачи запроса gateway для provider dispatch,
включая timeout, транспортную ошибку и отсутствие usage. Стоимость по usage
отделяют от счетов провайдера. При missing/invalid usage резервируют верхнюю
плановую стоимость попытки до сверки, не считают её бесплатной. Неизвестная
верхняя стоимость блокирует следующий платный этап. Остаток в рублях считают
консервативно: 2500 минус известные расходы и верхние оценки неизвестных.
Перед каждым следующим вызовом проверяют, что его максимум и обязательный
остаток gate помещаются в оба лимита. Provider-side retries не включаются.

### Платные этапы и остановка

Перед **каждым** будущим платным этапом владелец отдельно явно подтверждает:

- точный clean HEAD и неизменную интегрированную версию кандидата
- hashes prompt и provider JSON Schema с descriptions, протокол и output cap
- безопасный model label и закрытую сверку configuration class
- список scenario/repeat, D/F/R, eligibility и порядок вызовов
- актуальные тарифы с датой и источником, валюту, налоги и верхнюю смету
- накопленные расходы, attempts, консервативный остаток и резерв завершения gate
- stop conditions и точное число разрешаемых попыток

Чистый HEAD без этих данных и approval не разрешает платный запуск.
Интерактивное `RUN 1` остаётся техническим барьером runner и не заменяет
явного разрешения владельца. Подтверждение этапа может охватывать конкретный
список одноответных порций, каждая из них требует review предыдущего ответа.

Runner сейчас продолжает пакет после hard FAIL и не принимает semantic verdict
во время run. Поэтому для этой инициативы используется только одна модель,
один `--scenario` и `--repeats 1` на запуск. Сначала plan mode без `--run`,
потом лишь отдельно разрешённая одноответная порция и review до следующей.
Для дополнительного repeat выполняют ещё одну такую порцию, связывая отчёты
в ручном разборе. Порядок заранее заморожен, `--repeats 2` и пакет из 39 ответов
не применяются. Это методика существующего benchmark, без изменения runner.

Первый подтверждённый критический blocker останавливает текущий прогон.
`REVIEW_NEEDED` приостанавливает следующие вызовы до независимого разбора,
транспортный или validation failure оставляет gate неполным. Повтор запроса
ради удачного ответа запрещён. После дефекта первого кандидата второй возможен
только в оставшемся слоте, с адресной гипотезой и новым approval.

После двух неудачных кандидатов, исчерпания любого лимита или невозможности
завершить обязательный gate эксперимент прекращается с baseline и отрицательным
либо неполным результатом. Если финальная F выявила дефект, её outputs нельзя
использовать для настройки и затем выдавать тот же набор за независимый.
После выполнения критериев дальнейший prompt-tuning прекращается, остаток не
расходуется. Новый цикл, расширение выборки или новая модель требуют отдельного
решения владельца. Отрицательное завершение исследования #307 не означает
достижения продуктовой цели v0.3.

## Исторический финальный pre-beta gate

После очистки corpus вычисляют его фактический размер `N`. В начале запуска
проверяют representative compatibility prefix:

- `unknown-remedy-lighting`
- `unconfirmed-remedy-lighting`
- `desired-actions`
- `lighting-elevator-cabin`

Эти четыре scenario входят в общий corpus budget. Если prefix содержит blocker,
запуск останавливают и остальные paid requests не выполняют.

После успешного prefix каждый оставшийся актуальный scenario выполняют один
раз. Дополнительные повторы получают только заранее перечисленные критические
бывшие regressions с конкретным продуктовым обоснованием. До запуска фиксируют:

- итоговый `N`
- список критических scenarios
- общее максимальное число запросов
- точные команды и confirmation strings
- pricing snapshot и максимальную стоимость
- правила ранней остановки

Нельзя сохранять историческое число scenarios или прежний потолок запросов
искусственно. Любой новый hard fixture требует текущего продуктового инварианта.
Реальные запросы выполняются только после нового явного разрешения.

После успешного corpus gate отдельная задача #169 проверяет сквозной release
path browser → CAPTCHA → backend → provider, production configuration,
безопасную ошибку, защиту расходов, runtime и rollback.

## Квалификация #206 и перенос в production

[Финальная квалификация #206](https://github.com/ashikov/uo-request-generator/issues/206)
успешно завершена на YandexGPT 5.1 Pro через Responses для кандидата
`75d82dd71e3a7fa8bfd6d581388d7a0e8290e15f`. RUN 12 завершил 12/12 попыток:
74/74 hard checks, 10 semantic PASS, 2 QUALITY, 0 REGRESSION и 0 REVIEW_NEEDED.
QUALITY относится к пропущенному указанию нормальной работы загрязнённой двери,
а не к выдуманному техническому дефекту или ремонту. Предшествующая
офлайн-переоценка сохранённых 29 ответов дала 156/156 hard checks,
23 PASS, 5 QUALITY, 1 ACCEPTED_LIMITATION и 0 REGRESSION.
Исторические отрицательные результаты этим не переписываются.

При доставке #246/#249 в `main` на
`c1db5ad98612f0ed2b4f7844350a84594a2cc8ac` изменились относительно кандидата
только правила работы с репозиторием. Prompt, provider JSON Schema вместе с
descriptions, сериализация ввода, parser, renderer и диагностический код
сохранены без изменений. Это основание выбора модели, но не доказательство
соответствия любой фактической production-конфигурации.

Проверка исходного отчёта RUN 12 при подготовке #229 выявила различие:
`maxOutputTokens` был равен **1200**, тогда как production gateway отправляет
**4000**. Все 12 ответов использовали от 54 до 99 выходных токенов, то есть
прежний предел не был достигнут.

Решение #229 от 08.09.2026: различие **1200 → 4000 не отменяет квалификацию**.
Успешные ответы были существенно короче обоих пределов, а production-лимит
повышен, а не уменьшен. Prompt, schema/descriptions, сериализация ввода,
Responses и архитектура одного provider-вызова сохранены. Добавленный контроль
отключения логирования не меняет тело запроса. Этих данных достаточно для
узкого переноса при совпадении модели и остальных параметров с одобренным
классом, без повторного benchmark. Это не доказательство эквивалентности любых
настроек или статистической устойчивости будущих ответов.

До завершения #229 обязательны закрытая сверка фактической конфигурации и один
успешный реальный вызов на окончательных production-настройках с синтетическим
неперсональным вводом. Проверяются принятие параметров, завершение ответа,
строгая валидация и сохранение смысла примера без домыслов. Цель — один успешный
запрос, общий предел — два обращения к провайдеру. Второе разрешено только после
явного временного транспортного сбоя или сбоя провайдера. Смысловую ошибку нельзя
повторять ради успешного результата. Сохраняются только безопасные агрегаты.
Эта проверка не повторяет #206 и не выполняет browser/CAPTCHA gate #169.

Подготовка конфигурации в репозитории сама не запускает платную проверку.
Без подтверждённого соответствия настроек перенос остаётся незавершённым.
Операторский допуск, источник production-лимита и порядок переключения описаны
в [production runbook](PRODUCTION_RUNTIME.md#модель-production).
