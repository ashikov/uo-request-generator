# ADR-0004: Детерминированная граница требований первичной заявки

- Статус: принято, прежняя модель процедурных ролей заменена
- Дата: 2026-09-05
- Связанные задачи: #206, #233, #244

## Контекст

Первичная заявка должна одновременно сохранять пользовательский смысл и не
выдавать предположение модели за подтверждённый способ ремонта. Свободный
LLM-текст подходит для естественной нормализации описания проблемы, но не даёт
структурной гарантии происхождения технического требования.

Ранее ADR вводил закрытые процедурные роли, селекторы исходных фрагментов и
распределение `desiredActions` между предварительной проверкой, устранением и
проверкой результата. Эта схема уменьшала пространство для произвольного
технического текста, но оставляла модели сложную задачу, которая не давала
достаточной пользовательской ценности для public beta. Она также делала
provider-контракт зависимым от наличия `desiredActions`.

Точное совпадение фрагмента с исходным вводом доказывает его происхождение, но
не доказывает корректность смысловой роли или техническую истинность. Поэтому
exact provenance нельзя использовать как замену продуктовой семантике.

## Решение

LLM выполняет один вызов и возвращает только:

- `outcome: generated | multiple_issues`
- `title`
- `problem`
- `circumstances`
- `impact`
- `subject`
- `warnings`

Provider JSON Schema не зависит от наличия `desiredActions`. Она меняет
допустимую форму `subject` только в соответствии с состоянием
`confirmedProblemSubject`.

Backend формирует массив `requestItems` ровно из одного элемента:

- без `desiredActions` — фиксированное требование `Устранить наблюдаемую проблему`
- с `desiredActions` — весь проверенный пользовательский текст после минимальной
  нормализации представления

Минимальная нормализация удаляет пробелы по краям, заменяет переводы строк
пробелами, удаляет один начальный префикс `Прошу:` и безопасно переводит первую
букву в прописную. Она не сегментирует, не сокращает и не переписывает смысл.
Если пользователь указал действие, общий автоматический пункт рядом не
добавляется.

В provider-контракте и внутренней модели отсутствуют процедурные роли,
распределение действий, селекторы фрагментов и отдельный раздел проверки.
Неизвестность пользователя сохраняется в описательном тексте. Renderer
детерминированно добавляет нормативные основания и один нумерованный пункт в
разделе `Прошу:`.

## Сохранённые границы безопасности

Subject evidence gate остаётся fail closed. Предметный нормативный модуль
добавляется только при совпадении подтверждённого пользователем предмета,
provider-facing `subject.kind` и дословного evidence из исходного ввода. LLM не
выбирает законодательство.

Описание с несколькими местами не становится автоматически несколькими
проблемами. Несколько несвязанных проблем по-прежнему возвращают
`multiple_issues`.

Prompt запрещает придумывать причины, повреждения, последствия и технический
способ ремонта. Эти правила уменьшают риск, но генеративные `title`, `problem`,
`circumstances`, `impact` и `warnings` остаются semantic risk. Их полноту,
непротиворечивость и отсутствие домыслов проверяет live corpus и независимый
semantic review.

Evaluation-path сохраняет privacy-safe трассу границ provider-вызова и разбора:
первый отказавший этап, классификацию status/error, usage и санитизированную
структурную диагностику. Он использует те же правила приёма provider response,
что production. Materialization имеет только результат `PASS` или `FAIL`; коды
и location прежней процедурной онтологии удалены вместе с ней.

## Последствия

Положительные последствия:

- provider output не может создать request item или конкретный ремонт в разделе
  требований
- явное `desiredActions` сохраняется целиком вместе с отрицаниями и условиями
- описание без `desiredActions` всегда получает безопасный общий пункт
- provider response schema одинакова при наличии и отсутствии `desiredActions`
- внутренний `PrimaryRequestDraft` прямо отражает beta-продукт через
  `requestItems`
- публичные `GenerateRequestInput` и `GenerateRequestResult` не меняются

Ограничения:

- общий пункт намеренно менее специфичен, чем возможное процедурное обогащение
- авторитетность `desiredActions` означает происхождение от пользователя, а не
  техническую доказанность предложенного способа
- LLM по-прежнему может добавить неподтверждённый ремонт в генеративный prose,
  поэтому естественность и семантическая точность описательных полей требуют
  live eval

## Проверка

Автоматические тесты должны подтверждать:

- ровно один request item для каждого `generated` результата
- отсутствие общего пункта рядом с явным `desiredActions`
- сохранение полного составного текста, отрицаний и условий
- отсутствие обрезания на границе лимита тела
- отсутствие полей требований и прежних процедурных полей в provider schema
- равенство provider schema при одинаковом subject-контексте независимо от
  `desiredActions`
- неизменность subject evidence gate, нормативного потока и
  `multiple_issues`

Live eval проверяет только оставшиеся генеративные риски. Без нового
подтверждённого пользовательского сценария процедурная онтология в beta-контракт
не возвращается.
