# ADR-0005: Эксперимент с нормализацией пользовательского требования

- Статус: proposed
- Дата: 2026-09-09
- Связанная задача: #267

## Контекст

Принятый вариант A из [ADR-0004](0004-deterministic-evidence-gate.md) сохраняет
происхождение требования: backend использует весь `desiredActions` после
минимальной нормализации представления. Однако разговорное «Прекратите потоп!»
остаётся разговорным пунктом официальной заявки.

Кандидат B — ограниченный эксперимент с нормализацией этого текста в том же
единственном LLM-вызове. Он реализуется только в Draft PR и не считается
принятым решением для production. Результаты прежней квалификации A и
ADR-0004 сохраняют историческое значение, но не квалифицируют B.

## Предложенный контракт

В универсальный provider draft добавляется только одно обязательное nullable
поле `requestItem: string | null`. Его схема одинакова при наличии и отсутствии
`desiredActions`, при одинаковом контексте `subject`, и общая для Chat
Completions и Responses. Строка проходит действующие проверки представления и
лимита единственного пункта. Отсутствующее поле, неверный тип, пустая или
невалидная строка и неизвестные поля остаются controlled invalid-response
ошибками.

Backend формирует массив `requestItems` ровно из одного элемента:

| Исходный ввод | Валидное поле `requestItem` | Итоговый пункт |
| --- | --- | --- |
| Есть `desiredActions` | Непустая строка | Строка модели |
| Есть `desiredActions` | `null` | Полный исходный `desiredActions` после существующей минимальной нормализации представления, как в A |
| Нет `desiredActions` | `null` или непустая строка | `Устранить наблюдаемую проблему` |

`null` при явном требовании — разрешённый отказ от переформулировки, а не
ошибка всей генерации. Backend не подменяет исходный текст общим требованием,
не делает retry или второй provider call. Без `desiredActions` строка модели
игнорируется после структурной проверки. Даже составное требование остаётся
одним элементом. Заголовок `Прошу:`, нумерация, разделители, финальная пунктуация
и проверка общего лимита `body` принадлежат backend. Усечения текста нет.

## Семантическая граница

Единственный источник действий для `requestItem` — `desiredActions`. Модель
может убрать разговорную оболочку, эмоциональность и мат, сохраняя все явно
названные действия, их объекты, отрицания, условия, последовательность,
ограничения и пользовательскую степень определённости. Уже нейтральный текст
можно оставить почти неизменным. При невозможности безопасной нормализации
допустим `null`.

`problem`, `impact`, `subject` и другие поля не служат источниками новых
требований. Запрещено добавлять самостоятельные действия, технические причины,
неподтверждённые узлы, способы ремонта, исполнителей, сроки, документы или
гарантии. Диагностика не превращается в ремонт. Явно названный пользователем
узел можно сохранить в требовании, но это не делает его доказанной причиной.

`requestItem` не является source evidence для `subject` и не участвует в
выборе предметного нормативного модуля. Существующие subject evidence gate,
правовые основания, structured `location`, `multiple_issues` и публичный HTTP
контракт сохраняются. Процедурные роли, массивы provider-действий,
дополнительные semantic-поля и правило «минимум три пункта» не вводятся.

## Проверка и решение по эксперименту

Offline-тесты проверяют материализацию, fallback A, единственный пункт и вызов,
wire-схему, лимиты без усечения, privacy-safe диагностику и равенство
production/evaluation обработки. Они не доказывают смысловую безопасность
переформулировок. Диагностика может назвать поле `requestItem`, но не раскрывает
его содержимое.

Синтетические сценарии и
[отдельный план live-проверки](../experiments/request-item-normalization-live-plan.md)
задают сохраняемый смысл, запрещённые добавления и допустимые вариации качества.
Будущая проверка охватывает весь ответ: `requestItem`, описательные поля,
`subject`, warnings и outcome. Для платных вызовов необходимо отдельное явное
подтверждение владельца с согласованными сценариями, повторами и бюджетом.
В рамках подготовки Draft PR provider requests, paid benchmark, live eval и
production inference не выполняются.

Любая существенная потеря отрицания, условия, ограничения или модальности,
добавление самостоятельного ремонта либо неподтверждённой технической
конкретики, а также регрессия соседних полей или gates блокируют B. Успешный
повтор не компенсирует небезопасный. Новый цикл настройки prompt требует
отдельного продуктового решения.

Перевод PR в Ready, merge и rollout запрещены до semantic/live qualification,
независимого review и отдельного решения владельца. Если B не проходит
ограниченную проверку, Draft PR отклоняется и для beta остаётся A. При принятии
B связанные продуктовые и архитектурные документы обновляются согласованно,
а статус этого ADR меняется только после решения владельца.
