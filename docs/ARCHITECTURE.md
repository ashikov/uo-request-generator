# Архитектура

## Общая схема

Проект устроен как pnpm-монорепозиторий и модульный монолит. В production
запускается один Fastify-процесс в одном контейнере.

```mermaid
flowchart LR
    Browser[HTML, CSS и browser JavaScript] --> Route[Fastify API]
    Route --> Limiter[Клиентский limiter]
    Limiter --> Captcha[SmartCaptcha]
    Captcha --> Safeguard[Общий предохранитель LLM-вызовов]
    Safeguard --> Adapter[OpenAiCompatibleGateway / DisabledLlmGateway]
    Route --> Core[Схемы и порт core]
    Adapter --> LLM[OpenAI-compatible провайдер]
    Adapter --> Outcome[Готовая заявка / Несколько несвязанных проблем]
```

## Модули

- `apps/web` содержит Fastify-сервер, HTTP-маршруты и статические файлы формы
- `packages/core` содержит Zod-схемы, типы, интерфейс `LlmGateway`, расширенный
  черновик первичной заявки и его детерминированный renderer
- `packages/llm` реализует `DisabledLlmGateway` и провайдер-независимый
  `OpenAiCompatibleGateway` для совместимых подмножеств Chat Completions и
  Responses API

`web` зависит от `core` и `llm`, а `llm` зависит от `core`. Пакет `core` не знает
о Fastify, HTTP, браузерном коде, переменных окружения приложения и
LLM-провайдерах.

## Расширенный черновик первичной заявки

Provider-independent `PrimaryRequestDraft` находится в `packages/core`. Его
строгая Zod-схема различает смысловые роли, а `renderPrimaryRequestDraft`
собирает публичный `GenerateRequestResult` в фиксированном порядке:

```text
problem
→ circumstances, если есть
→ impact, если есть
→ verification, если есть
→ COMMON_LEGAL_BASIS_BLOCK
→ предметный нормативный абзац, если пользователь явно подтвердил предмет
  и происхождение evidence проверено
→ Прошу: и actionPlan в порядке preliminaryCheck, remedyActions, resultCheck
```

Renderer не выводит индивидуальные факты из других полей. `null` полностью
пропускает необязательную часть, поэтому не остаются пустые заголовки и лишние
разделители. Общие и предметный нормативные тексты хранятся в `packages/core` и
не входят в динамические данные черновика. Подробный контракт нормативного
модуля и источники зафиксированы в
[`REQUEST_RULES.md`](REQUEST_RULES.md#предметный-нормативный-модуль).

Лимиты выбраны по масштабу смысловых ролей и проверены синтетическими fixtures:

| Поле | Роль | Лимит |
| --- | --- | ---: |
| `title` | Краткий заголовок | 120 символов |
| `problem` | Наблюдаемая проблема | 1526 символов |
| `circumstances` | Существенные обстоятельства | 600 символов |
| `impact` | Последствия, практическое значение и риски | 500 символов |
| `verification` | Обстоятельства для проверки | 500 символов |
| `actionPlan.preliminaryCheck` | Проверка до устранения | 500 символов или `null` |
| `actionPlan.remedyActions` | Действия по устранению | От 1 элемента |
| `actionPlan.resultCheck` | Проверка результата | 500 символов или `null` |
| Элемент процедурного плана | Одно действие | 500 символов |
| Процедурный план | Итоговые требования | Не более 5 элементов |
| `warnings` | Предупреждения | До 5 элементов по 200 символов |
| `confirmedProblemSubject` | Явное подтверждение предмета проблемы | Необязательный enum |
| `subject.evidence` | Дословные фрагменты исходного ввода | 1–2 фрагмента по 10–300 символов |
| Динамическая часть и требования | Текст без нормативного блока | 1537 символов |
| Готовый `body` | Все части с максимальным нормативным блоком | 2500 символов |

Лимит `problem` оставляет место для максимального нормативного блока и
минимального требования даже на своей точной границе. Остальные поля
ограничивают самостоятельные дополнительные абзацы, а итоговый лимит `body` не
позволяет одновременно исчерпать все частные пределы. Превышение любого предела
приводит к ошибке валидации без обрезания.

`title`, `warnings` и полный `body` следуют публичному контракту результата.
Лимиты `impact` и отдельного действия сохраняют до 500 символов явно переданных
`consequences` и `desiredActions`, а также допускают компактное безопасное
смысловое и процедурное обогащение. Для новых самостоятельных абзацев выбраны
600 символов обстоятельств и 500 символов предмета проверки. Подробный fixture
входной двери сохраняет необходимые сведения без дополнительных процедурных
требований и не добавляет устранение неподтверждённых повреждений.

Семантика процедурного плана зафиксирована в
[`REQUEST_RULES.md`](REQUEST_RULES.md#процедурный-план-первичной-заявки). Core
проверяет формулу `preliminaryCheck + remedyActions.length + resultCheck <= 5`,
не обрезает план и детерминированно разворачивает заполненные роли в непрерывную
нумерацию.

Provider-facing generated-ветка содержит те же смысловые части, nullable
`subject` и поле `outcome`. `subject` описывает только предмет проблемы и
содержит дословные фрагменты исходного ввода с именами полей. Локальная
Zod-схема расширяет `primaryRequestDraftSchema`, поэтому переиспользует её
строковые, количественные и итоговый `body`-лимиты. После проверки gateway
удаляет discriminator и передаёт `PrimaryRequestDraft` единственному renderer
вместе с исходным `GenerateRequestInput`.

### Предлагаемая граница ADR-0004

Proposed ADR-0004 сохраняет provider-authored prose для `title`, `problem`,
`circumstances`, `impact` и `warnings`, но заменяет свободные `verification` и
`actionPlan` закрытыми procedural decisions. После одного provider call
`packages/llm` проверяет strict JSON shape, а provider-independent materializer
в `packages/core` проверяет exact evidence и строит защищённые роли существующего
`PrimaryRequestDraft`. Текущий renderer и public result остаются последним
этапом без изменения.

```text
GenerateRequestInput
→ один provider call
→ generative prose + bounded procedural decisions
→ strict provider schema
→ core evidence validation и procedural materializer
→ PrimaryRequestDraft
→ существующий deterministic renderer
→ GenerateRequestResult
```

Hard boundary запрещает arbitrary technical method slot в `verification`,
`preliminaryCheck`, `remedyActions` и `resultCheck`, сохраняет множественный
procedural plan и отклоняет malformed или structurally inconsistent decisions
fail closed. Набор решений описывает общие операции: сохранить пользовательскую
неопределённость, установить неизвестную причину, устранить наблюдаемую
проблему, установить явно отсутствующий элемент, выполнить backend-owned
explicit action и проверить устранение проблемы.

`desiredActions` остаётся backend-owned authoritative source и не требует
полного эха модели. Для семантически атомарного действия provider выбирает
`whole`, а для составного значения распределяет один или несколько exact
source fragments между `preliminaryCheck`, `remedyActions: 1..N` и
`resultCheck`. Materializer берёт текст только из исходного input и выполняет
ограниченную presentation normalization: trim, замену переводов строк пробелом
и удаление одного начального `Прошу:`. Правильность segmentation, полнота
explicit actions и semantic allocation остаются live-eval guarantees.

Schema не содержит ремонтов, компонентов, инженерных систем, причин или
symptom-to-remedy mappings. Exact evidence подтверждает provenance, но не
семантическую правильность intent. Естественность descriptive prose,
non-invention, полнота фактов, impact, группы, location и cross-role semantic
duplication остаются semantic/live acceptance. Equality evidence quotes не
используется как hard deduplication check.

Эта граница пока существует только как Proposed ADR и test-only proof
`packages/core/tests/task-243-selective-procedural-gate*.ts`. Production gateway
по-прежнему использует описанный ниже свободноформатный generated draft. #233
может быть закрыта только после отдельного wiring и acceptance.

Публичный вход содержит необязательное поле `confirmedProblemSubject`,
принимаемое как закрытый enum. Форма отправляет его только после выбора пункта в
`select`. Проверенное значение сохраняется в HTTP/core-вводе и не сериализуется
в LLM user message. При подтверждении общий provider-facing prompt содержит
правила всех поддержанных основных предметов, а JSON Schema допускает любой
поддержанный `subject.kind` или `null`. Без подтверждения schema допускает
только `subject: null`. Backend сравнивает полученный `subject.kind` с исходным
входом.

Core проверяет каждый evidence-фрагмент точным совпадением со значением
указанного поля входа. Это подтверждает происхождение цитаты, но не её смысл.
Дверной модуль, модули освещения и уборки помещения общего пользования, а также
модули кровли, вентиляции общего имущества и лифта подключаются только когда
`confirmedProblemSubject` совпадает с provider-facing `subject.kind` и всё
evidence сходится при проверке. Отсутствие
любого условия, `subject: null` или вызов renderer без исходного ввода оставляют
только два общих основания. Сопоставление не использует keyword routing, regex
или semantic matching.

Worst-case длина общего и предметного нормативных текстов резервируется до
provider request для любого ввода. Поэтому prompt, provider-facing схема и core
используют один предел динамической части 1537 символов, а core всегда проверяет
черновик с учётом максимального нормативного блока. Публичный предел 2500
символов не изменён, усечение отсутствует.

## Поток генерации

Перед отправкой форма получает существующую public configuration из
`GET /api/captcha/config`. В ней `generationAvailable` сообщает только
доступность генерации без причины, лимитов или секретов. При `false` browser
показывает нейтральное сообщение и не загружает SmartCaptcha, не получает token
и не вызывает `POST /api/generate`.

При `generationAvailable=true` форма проверяет базовые ограничения в браузере и
отправляет JSON в `POST /api/generate`. Обязательным остаётся только
`description`; пустые необязательные значения не отправляются. Поля
`consequences` и `desiredActions` ограничены 500 символами, как `impact` и
отдельное действие внутреннего черновика: оба поля передают сведения того же
предметного масштаба.
Fastify-маршрут валидирует отдельную строгую транспортную схему, которая
добавляет к предметным полям необязательный `captchaToken`. После валидации
токен отделяется на HTTP-границе и не попадает в `packages/core`. Затем маршрут
получает штатный `request.ip`, проверяет ранее установленный подписанный
технический идентификатор браузера и при необходимости только подготавливает
новый. После атомарного допуска клиентским limiter обязательный режим проверяет
CAPTCHA. Затем общий предохранитель атомарно допускает вызов. Только успешно
проверенный или явно отключённый CAPTCHA-режим с допуском предохранителя вызывает
`LlmGateway`.

До JSON parsing маршрут применяет встроенный Fastify `bodyLimit` в 45 635 байт.
Граница складывается из максимальной длины всех входных полей, самого длинного
`confirmedProblemSubject`, максимального CAPTCHA-токена, шести байт на один
UTF-16 code unit при JSON escaping, фактической структуры JSON и служебного
запаса 2 048 байт. Превышение возвращает безопасный HTTP 413 с кодом
`request_too_large` до limiter, CAPTCHA, общего предохранителя и LLM.

`LlmGateway.generateRequest()` возвращает типизированный outcome. Ветка
`generated` содержит существующий `GenerateRequestResult`, а
`multiple_issues` сообщает, что во вводе несколько самостоятельных несвязанных
проблем. Во втором случае маршрут возвращает контролируемую ошибку HTTP 400 с
публичным кодом `multiple_issues` и не формирует готовый текст заявки.

Route-level `onRequest` сначала создаёт `requestId` и metadata-only начальное
событие. Затем он делает non-consuming проверку доступности генерации. При
`GENERATION_ENABLED=false` маршрут сразу записывает metadata-only итоговое
событие и возвращает существующий `503 generation_unavailable`; handler не
использует body, не создаёт client ID и не меняет защитное состояние.

Для доступной генерации порядок проверок остаётся следующим:

```text
requestId и non-consuming availability guard
→ transport body limit
→ JSON parsing
→ валидация входных данных
→ клиентские лимиты
→ серверная проверка CAPTCHA
→ общий предохранитель LLM-вызовов
→ LlmGateway
```

Невалидный запрос не создаёт техническую cookie и не расходует квоты.
Отклонённый лимитером запрос не обращается к verifier или gateway. Проверка
CAPTCHA, общий предохранитель и gateway занимают уже допущенный active-слот
limiter, который освобождается во внешнем `finally` после любого исхода.

## Структурированное логирование генерации

Route-level `onRequest` создаёт контекст генерации до разбора JSON body. Контекст
хранится в экземпляре Fastify request и содержит уникальный UUID `requestId`,
момент начала запроса и признак выполненной попытки записи итогового события.
Он сохраняется и для отключённой генерации, чтобы прямой технический отказ можно
было безопасно сопоставить с двумя metadata-only events. Основной handler и route
`errorHandler` используют один контекст, включая некорректный JSON и ошибки
подготовки client id или limiter. Глобального изменяемого состояния нет.

Маршрут передаёт `requestId` в `LlmGateway.generateRequest(input, requestId?)` и
возвращает его клиенту в заголовке `x-request-id`. Ошибочные API-ответы также
содержат тот же `requestId`, но не раскрывают внутренние детали провайдера.
Интерфейс показывает полученное понятное сообщение и полный `requestId` как
технический код запроса. Для невалидного API-ответа или ошибки до получения
ответа браузер не создаёт технический код самостоятельно.

Каждый начатый запрос выполняет одну попытку записи JSON-строки
`generation_started` и одну попытку записи соответствующей итоговой JSON-строки
с тем же `requestId`:

- `generation_succeeded` со статусом `generated`
- `generation_rejected` со статусом `request_too_large`, `validation_error`,
  `multiple_issues`, `rate_limited`, `captcha_failed`, `captcha_unavailable` или
  `generation_unavailable`
- `generation_failed` со статусом `provider_unavailable`, `timeout`,
  `network_error`, `invalid_response` или `internal_error`

Начальное событие содержит `event`, `requestId` и `timestamp`. Итоговое событие
дополнительно содержит `status`, `durationMs` и фактический `httpStatus`
публичного ответа. После реально выполненного вызова metadata-capable gateway
итоговое событие содержит безопасный вложенный объект `llm`: provider, полное
имя model, нормализованный usage, `usageStatus`, SHA-256 hash точного system
prompt и `durationMs` обращения к провайдеру. Верхнеуровневый `durationMs`
остаётся длительностью всего HTTP-запроса.

Событие `generation_failed` для внешнего ответа провайдера с non-2xx может
дополнительно содержать только проверенный failure-only `providerHttpStatus`:
целое число от 100 до 599, и только при статусе `provider_unavailable`. Для
`timeout`, `network_error` и `invalid_response` это поле отсутствует. Это status
ответа провайдера, а не публичный `httpStatus` ответа `/api/generate`. Например,
публичный ответ может иметь status `503`. Поля не содержат сырых диагностических
данных провайдера или пользователя.

Usage нормализуется из фактического ответа провайдера в `inputTokens`,
`outputTokens` и `totalTokens`. При отсутствии usage он равен `null` со статусом
`missing`, а при частичных или невалидных данных — `null` со статусом `invalid`.
Это не делает успешную генерацию ошибкой и не вычисляет токены самостоятельно.
Hash system prompt служит воспроизводимым идентификатором: одинаковый точный
текст даёт то же значение, изменение текста — другое. Для событий выполняются
попытки записи в stdout по одной строке без пользовательского ввода, готовой заявки,
prompt, response body, API keys, `Authorization`, CAPTCHA token, cookies,
полный набор headers или `process.env`.

Попытки записи событий синхронны и не влияют на исход запроса. Неудачная попытка
записи `generation_started` не останавливает валидацию, проверки безопасности и
генерацию, а неудачная попытка записи итогового события не меняет уже выбранный
исход: успешную генерацию, контролируемый отказ или ошибку. Повторная попытка
записи и второе итоговое событие не выполняются. Вместо этого выполняется одна
попытка записи в stderr JSON-строки `generation_event_write_failed` только с
фиксированными техническими полями: `event`, `requestId` и `failedEvent` с именем
незаписанного события. Неудача этой диагностической попытки также не влияет на
запрос.

Пакет `llm` классифицирует контролируемые ошибки через
`GenerationProviderUnavailableError` и его наследников
`GenerationTimeoutError`, `GenerationNetworkError` и
`GenerationInvalidResponseError`. Gateway проверяет состояние созданного им
`AbortSignal.timeout()` как при ожидании HTTP response, так и при чтении body.
Обычная transport failure остаётся `network_error`, а ошибка разбора ответа без
timeout — `invalid_response`. Для настроенного gateway эти статусы сохраняются
в событиях, а клиент получает нейтральное сообщение о временной недоступности
генерации. `DisabledLlmGateway` отдельно сообщает, что генерация пока не
подключена.

## Общий предохранитель LLM-вызовов

`apps/web` создаёт один `GenerationSafeguard` на экземпляр Fastify-приложения.
После CAPTCHA его синхронный `acquire()` сначала проверяет аварийное отключение,
затем границу календарных суток UTC, дневной предел и общую ёмкость. Только после
всех проверок он увеличивает дневной счётчик и занимает active-слот. Отклонение
из-за ёмкости не расходует дневную попытку.

Суточный счётчик сбрасывается при первом обращении в следующих календарных
сутках UTC, но active-слоты при смене суток не сбрасываются. `release()`
идемпотентно освобождает только active-слот во внутреннем `finally` после успеха,
контролируемой ошибки gateway или неизвестного исключения. Допущенная попытка
остаётся учтённой независимо от результата gateway.

Это внутрипроцессная защита от массового расхода, а не точный денежный бюджет.
Перезапуск процесса сбрасывает суточный счётчик. Несколько экземпляров не имеют
общего состояния, поэтому Redis, provider usage, фактические расходы и
операторские отчёты относятся к другим issue.

## Клиентский limiter

`apps/web` создаёт один `GenerationRateLimiter` на экземпляр Fastify-приложения.
Limiter не относится к предметной логике заявки и не входит в `packages/core`.
Он хранит только IP-ключи, случайные технические идентификаторы, UTC-границы
суток, временные отметки и счётчики. Пользовательский ввод и результат генерации
в это состояние не попадают. IP, cookie, подпись, секрет и внутренние значения
счётчиков не включаются в публичные ошибки и логи.

Допуск выполняется одной операцией. Сначала удаляются истёкшие IP-отметки и
суточные записи, затем без изменения состояния проверяются скользящее IP-окно,
суточная квота технического клиента, его активный слот, консервативный
active-IP fallback и общая ёмкость хранилища. Установленный клиент проверяет
active-слот только по своему UUID. Запрос без валидной cookie отклоняется, если
с того же IP уже выполняется любая генерация. Поэтому разные установленные
клиенты за одним IP могут работать параллельно, а два первых запроса без cookie
сериализуются.

Если сработала хотя бы одна проверка, независимые квоты не изменяются и
подготовленный UUID не отправляется клиенту. При допуске одновременно
добавляется IP-отметка, увеличивается суточный счётчик, захватывается active-слот
клиента и увеличивается число активных запросов IP.

Активный слот освобождается в `finally` после успеха, контролируемой ошибки
CAPTCHA, технической недоступности verifier, ошибки gateway или неизвестного
исключения. Там же уменьшается число активных запросов IP, а запись удаляется
после завершения последнего запроса с этого адреса. IP- и суточная квоты уже
допущенной попытки остаются израсходованными независимо от результата CAPTCHA
или gateway.

Технический UUID передаётся в подписанной cookie `uo_generation_client` с
атрибутами `HttpOnly`, `SameSite=Strict`, `Path=/` и ограниченным сроком жизни.
Для HTTPS-запроса добавляется `Secure`. Подпись создаёт и проверяет официальный
плагин `@fastify/cookie`. Неподписанное, повреждённое или не соответствующее
формату UUID значение не используется. Replacement cookie возвращается только
после успешного допуска limiter.

По умолчанию Fastify получает `trustProxy: false` и не доверяет
proxy-заголовкам. `GENERATION_TRUSTED_PROXIES` принимает разделённый запятыми
allowlist буквальных IPv4, IPv6 и CIDR. После строгой проверки приложение
передаёт непустой массив Fastify через его штатный `trustProxy`. DNS-имя, `*`,
число hop, пустой элемент, некорректный адрес или CIDR останавливают запуск. Код
приложения сохраняет штатные `request.ip` и `request.protocol` и не разбирает
`X-Forwarded-For` или `X-Forwarded-Proto`.

Allowlist должен содержать только фактические адреса или сети доверенных proxy и
обновляться при изменении proxy-цепочки. Backend не должен иметь прямого
публичного доступа в обход proxy, а proxy обязан перезаписывать forwarding-
заголовки данными фактического соединения. Настройка приложения дополняет, но не
заменяет сетевое ограничение доступа.

Legacy-переменная `GENERATION_TRUST_PROXY` больше не поддерживается: её наличие
останавливает запуск, чтобы оператор не считал старую boolean-настройку
действующей. Для миграции её нужно удалить и задать явный allowlist в
`GENERATION_TRUSTED_PROXIES`.

Состояние ограничено `GENERATION_RATE_LIMIT_STATE_CAPACITY`. Каждая IP-отметка,
суточная запись, active-слот клиента и active-IP запись учитываются в ёмкости.
Очистка выполняется детерминированно при обращении без фонового таймера. Если
после очистки для нового допуска недостаточно места, запрос отклоняется без
удаления актуальных записей.

Limiter рассчитан на один процесс MVP. Его счётчики и эфемерный секрет
отключённого локального gateway сбрасываются при перезапуске. Redis,
распределённая синхронизация и общие лимиты между несколькими экземплярами не
реализованы.

Public configuration кэшируется на время жизни страницы. Поэтому backend early
guard остаётся авторитетной проверкой для прямого запроса и вкладки, которая
сохранила более ранний availability snapshot.

## SmartCaptcha

`apps/web` представляет конфигурацию как discriminated union: `{ mode:
"disabled" }` либо `{ mode: "required", clientKey, serverKey }`. В обязательном
режиме отсутствие любого ключа останавливает запуск. Для локального запуска с
`DisabledLlmGateway` отсутствие `SMARTCAPTCHA_MODE` эквивалентно отключённому
режиму, но конфигурация подключённого LLM всегда требует явного режима.

`GET /api/captcha/config` всегда возвращает boolean `generationAvailable`,
`required` и, в обязательном режиме, клиентский ключ. Browser JavaScript строго
проверяет число и тип полей ответа. При `generationAvailable=false` он не
загружает внешний script и не отправляет generation request. В режиме `required`
доступной генерации он расширенным методом загружает официальный скрипт,
отрисовывает виджет с `invisible: true` и `hideShield: true`, показывает
встроенное уведомление об обработке данных, вызывает `execute` после локальной
валидации и передаёт callback-токен только в транспортном теле генерации. После
каждого результата выполняется `reset`, поэтому следующая попытка не
переиспользует токен.

Конкретный `SmartCaptchaVerifier` использует встроенный `fetch` и отправляет
`secret`, `token` и штатный `request.ip` формой на endpoint проверки
SmartCaptcha. Код не разбирает forwarding-заголовки самостоятельно. Запрос
ограничен timeout, а чтение ответа — небольшим пределом байтов. Verifier не
делает retry и возвращает только `verified`, `failed` или `unavailable`, не
перенося внешнее поле `message` во внутренний контракт.

Только строгий ответ `status: "ok"` с непустым `host` считается успешным.
`status: "failed"` означает пользовательский отказ. Timeout, сеть, non-2xx,
слишком большой ответ, некорректный JSON, неожиданная форма и `ok` с пустым
`host` означают `unavailable`. Это намеренный fail closed для платного endpoint,
включая HTTP-ошибки, которые документация провайдера предлагает обрабатывать
мягче.

Автоматические тесты внедряют `fetch`, verifier и объект
`window.smartCaptcha`, поэтому не выполняют запросы к внешнему сервису и не
требуют реальных ключей. Программная интеграция не означает, что CAPTCHA
включена в публичном экземпляре: реальные ресурс, ключи и ручная сквозная
проверка относятся к #62. При использовании reverse proxy безопасное публичное
включение требует настроенного allowlist и сетевого ограничения доступа к
backend.

Gateway сериализует исходный пользовательский ввод одним JSON-объектом с полями
`description`, `location`, `consequences` и `desiredActions`. Необязательные
строки передаются после удаления пробелов по краям, а отсутствующие значения —
как `null`. `confirmedProblemSubject` остаётся в проверенном HTTP/core-вводе и
нужен backend после ответа для детерминированной проверки.
`description` остаётся свободным текстом и не считается готовым значением
выходного `problem`.

Gateway передаёт обоим LLM-протоколам один системный prompt и одну строгую JSON
Schema. При подтверждении prompt содержит правила всех поддержанных основных
предметов, а schema допускает любой поддержанный `subject.kind` или `null`.
Chat Completions получает schema через `response_format`, Responses API — через
Structured Outputs в `text.format`. Корневой объект содержит обязательное поле
`draft` с вложенным `anyOf`: одна ветка требует полный черновик `generated`,
другая допускает только пустой `multiple_issues`. Такая оболочка сохраняет
объект в корне совместимой схемы и одновременно запрещает смешивать оба исхода.
Для Responses сохраняется `strict: true`.

После извлечения текста общий предметный модуль всё равно выполняет `JSON.parse`
и строгую Zod-валидацию корневой оболочки и черновика. Локальная discriminated
union окончательно проверяет межполевые правила. Для `generated` обязательны
непустые `title` и `problem`, nullable `circumstances`, `impact` и
`verification`, nullable-предмет `subject` с проверяемым evidence, процедурный
план с одним или несколькими действиями и ограниченный массив предупреждений.
Для `multiple_issues` все строковые части, `subject` и `actionPlan` должны быть
`null`, а `warnings` — пустым массивом. Любое другое сочетание отклоняется fail
closed как невалидный ответ модели.

Детерминированное форматирование выполняется только для `generated`. После
успешной проверки provider-facing черновик передаётся расширенному renderer из
`packages/core` вместе с исходным вводом. Обычный TypeScript-код вставляет два
фиксированных общих нормативных основания в виде коротких связных абзацев,
разделённых пустой строкой, затем при явном пользовательском подтверждении
предмета и проверенном происхождении evidence добавляет один предметный абзац
без URL и формирует нумерованный раздел `Прошу:`, который завершает основную
часть заявки. Источники нормативных положений зафиксированы в
[`REQUEST_RULES.md`](REQUEST_RULES.md). Значение пользовательского подтверждения
не входит в provider user message и используется backend после ответа для
детерминированной проверки. LLM не получает тексты, идентификаторы модулей и
ссылки, не выбирает нормы и не делает дополнительный вызов.

Расширенный core-контракт проверяет полный `body` вместе с максимальным
нормативным блоком по публичному лимиту 2500 символов. Provider-facing локальная
схема переиспользует эту проверку без второго набора правил и без молчаливого
усечения. Внешний успешный контракт `POST /api/generate` по-прежнему содержит
только `title`, `body` и `warnings`.

Responses API по умолчанию получает `max_output_tokens: 4000`. Для консервативной
оценки учитывается весь 2500-символьный лимит итогового `body`, хотя нормативный
блок модель не возвращает, а также заголовок до 120 символов, предупреждения
суммарно до 1000 символов и JSON overhead. Лимит оставляет конечный запас на
токенизацию Structured Output, но не задаётся чрезмерно большим. В Chat
Completions сохраняется существующая форма запроса без отдельного поля лимита.

Классификация связанной и нескольких несвязанных проблем происходит внутри
этого же вызова LLM. Дополнительного запроса, автоматического retry, локальной
эвристики и классификации в браузере нет. При `multiple_issues` приложение не
выбирает одну проблему, не объединяет проблемы и просит пользователя составить
отдельные заявки.

Конфигурационный слой `apps/web` валидирует переменные окружения и передаёт в
`OpenAiCompatibleGateway` выбранный протокол, готовые URL, модель, ключ, схему
авторизации и identifier provider. `LLM_API_PROTOCOL` принимает
`chat-completions` или `responses`.
При отсутствии переменной для обратной совместимости выбирается
`chat-completions`. Протокол и provider не определяются по URL, модели или
схеме авторизации.

Встроенная Yandex AI-конфигурация детерминированно передаёт provider `yandex` и
не требует `LLM_PROVIDER`. Для custom `LLM_API_URL` обязательно задать
`LLM_PROVIDER` как стабильный lower-case ASCII identifier длиной до 64 символов
из букв, цифр, `_` и `-`. Неполная или невалидная custom-конфигурация fail
closed выбирает `DisabledLlmGateway`.

Yandex AI настраивается в этом слое как один из OpenAI-compatible провайдеров.
Для Chat Completions слой выбирает `/v1/chat/completions` и YandexGPT, для
Responses API — `/v1/responses` и Alice AI LLM Flash. Идентификатор каталога
передаётся gateway через общий механизм дополнительных заголовков, поэтому
пакет `llm` не зависит от Yandex AI.

При отсутствующей или неполной конфигурации используется `DisabledLlmGateway`,
возвращающий контролируемую ошибку `generation_provider_unavailable`.

## Ручной fixture-based smoke-runner

Исполняемый smoke-runner находится в `apps/web/tests/manual` и не входит в
production build. Он напрямую импортирует общий массив `scenarios` из тестовой
структуры `packages/core`, не требует публичного runtime-экспорта fixtures и не
создаёт отдельный пакет.

Runner проверяет конфигурацию до первого запроса и последовательно вызывает
`generateRequest` ровно один раз для каждого сценария. Retry, параллельные
вызовы, LLM-as-a-judge и дополнительные запросы для оценки результата
отсутствуют. Обычная ошибка сценария накапливается в итоговой сводке, а
контролируемая общая недоступность провайдера останавливает дальнейшие запросы.

Для `generated` runner сначала применяет публичную схему результата. Невалидный
результат получает безопасную категорию ошибки и не печатается. Для валидного
результата runner использует нормализованные данные Zod, выводит ручной отчёт и
только затем проверяет непустые `title` и `body`, соответствие предупреждений
fixture и отдельный нумерованный раздел `Прошу:` с количеством требований от
одного до пяти.
Предупреждения должны оставаться отдельным полем и не повторяться в тексте
заявки. Для `multiple_issues` автоматически успешным считается только
одноимённый outcome.

Итоговый счётчик отражает только сценарии, прошедшие все автоматические
проверки. Сохранение фактов, границу безопасного вывода и обоснованность
процедурных требований нельзя надёжно подтвердить без семантического судьи.
Поэтому runner выводит в stdout синтетический ввод, публичный результат и списки
`mustPreserveFacts` и `mustNotInvent` для ручной проверки, но не сохраняет
ответы в репозитории и не считает ручное решение.

## Протоколы LLM

Оба протокола используют общий механизм выбора system prompt и JSON Schema,
формирование пользовательского сообщения, HTTP-транспорт, таймаут, обработку
ошибок, разбор структурированного черновика и форматирование заявки. Различаются
только тело запроса, схема ответа и извлечение текста.

Системный prompt требует классифицировать свободное `description` по смыслу:
наблюдаемая проблема помещается в `problem`, существенные дополнительные факты —
в `circumstances`, а `impact` сохраняет переданные последствия и риски или
непосредственно выведенное практическое значение и потенциальный риск.
Предположения и неизвестные обстоятельства формулируются как предмет проверки в
`verification`. `actionPlan` отдельно содержит необходимую проверку до
устранения, одно или несколько действий по устранению и обоснованную проверку
результата. Явные `desiredActions` распределяются по этим ролям с приоритетом.
Один смысловой факт должен появляться ровно в одной динамической роли.

Выводимый риск допускается только как явно потенциальный и не может зависеть от
неизвестной причины, скрытого повреждения, отсутствующего оборудования или
многоступенчатой причинной цепочки. Prompt предпочитает нейтральное практическое
значение и ограничивает каскад рисков. Проверка, устранение и контроль результата
не являются обязательным шаблоном для каждого дефекта.

При нормализации эмоционального ввода конкретные сведения о человеке, месте и
обстоятельствах сохраняются и не заменяются выведенными категориями людей.

Локальная Zod-схема проверяет структуру ответа fail closed, но не определяет
смысловую эквивалентность формулировок. Отсутствие домыслов и смысловых повторов
дополнительно проверяется ручным просмотром полного LLM smoke-check.

Chat Completions получает `model`, `messages`, `temperature` и
`response_format` с выбранной строгой JSON Schema. Текст извлекается из
`choices[0].message.content`.

Responses API получает `model`, `instructions`, `input`, `temperature`,
`max_output_tokens` и `text.format` с типом `json_schema`, а также передаёт
`store: false`: приложение не использует сохранённое состояние ответа.
Structured Outputs уменьшают вероятность свободного или неполного текста, но не
заменяют общий локальный путь `JSON.parse`, Zod-валидации и форматирования,
который после извлечения текста совпадает с путём Chat Completions.
Yandex-compatible ответ может содержать
агрегированный текст в верхнеуровневом `output_text`. Стандартный сырой
HTTP-ответ Responses API передаёт текст в блоках `output[].content[]` с типом
`output_text`.

Если провайдер передал `status`, gateway принимает текст только при значении
`completed`. Отсутствие `status` допускается только для упрощённого совместимого
ответа с непустым верхнеуровневым `output_text`. Для обхода стандартного
вложенного `output[]` требуется `status: completed`. После этой проверки gateway
сначала использует непустой верхнеуровневый `output_text`, а при его отсутствии
последовательно объединяет `text` всех текстовых блоков в message-элементах.
Нетекстовые, неизвестные и refusal-блоки не попадают во внутренний текст. После
нормализации оба формата используют общие разбор черновика и форматтер. Проект
не зависит от SDK провайдера.

Локальный benchmark вызывает тот же `OpenAiCompatibleGateway` напрямую, без
Fastify, CAPTCHA, rate limiter и generation safeguard. Дополнительный метод
`generateRequestWithMetadata` сохраняет свой benchmark-контракт с optional
provider usage.
Production использует provider-independent metadata gateway, когда adapter его
поддерживает, для безопасного terminal event без передачи prompt или
пользовательских данных верхним слоям.

Benchmark строит request body общим helper, поэтому сериализация input,
production prompt, Structured Output schema, temperature и protocol-specific
response parsing не дублируются. Для Responses API output cap остаётся
`max_output_tokens`. Для Chat Completions benchmark добавляет `max_tokens` или
`max_completion_tokens` только по явному локальному выбору. Production config
этот параметр не задаёт, поэтому её request shape не меняется.

Streaming, tools, conversations, background responses и хранение `response_id`
не поддерживаются.

API не сохраняет и не логирует пользовательский текст или ответ LLM и не
возвращает фиктивную заявку. Контролируемый `multiple_issues` не содержит ввод,
ответ модели или технические подробности. Неизвестная ошибка возвращается как
`internal_error` без внутренних деталей.

## Завершение процесса

Первый `SIGINT` или `SIGTERM` запускает `app.close()`. Все последующие вызовы
shutdown используют уже начатую операцию и не создают конкурирующее закрытие.
Тот же путь используется после ошибки запуска сервера.

Graceful shutdown ограничен фиксированными 10 секундами. Успешное закрытие
завершает работу штатно. Ошибка `app.close()` устанавливает ненулевой код и
немедленно принудительно завершает процесс. Превышение срока также принудительно
завершает процесс с ненулевым кодом. Таймер очищается после успеха или ошибки
закрытия.

## Почему модульный монолит

Основной сценарий мал и выполняется синхронно. Один процесс упрощает разработку,
проверки и эксплуатацию, а границы пакетов отделяют доменные контракты от
интерфейса и будущей интеграции с LLM. Распределённая система сейчас не решает
практическую проблему проекта.

Для одной небольшой формы достаточно обычных HTML, CSS и минимального browser
JavaScript. Такой веб-слой сохраняет прямой путь от HTTP-запроса к доменному
порту и остаётся доступным для самостоятельного чтения и ревью. Если интерфейс
подтверждённо усложнится, его можно заменить без изменения `core` и LLM-границы.

## Намеренно отсутствующие части

Не реализованы выбор модели, хранение данных, учётные записи, фотографии,
индивидуальная юридическая квалификация, подбор законодательства, RAG,
интеграции с мессенджерами, автоматическая отправка, аналитика и отдельные
сервисы. Для них не создаются пустые модули.
